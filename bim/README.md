# bim — From Drawings to BIM (Task 2)

The source material we obtained is not a BIM model but **PDF drawings**. This module reconstructs room geometry
and finish build-ups from those drawings, loads them into the database, and exports them to IFC4.

```
Drawing PDF ──extract_plan──▶ room polygons + FL/SL levels
                                    │
                                    ▼
                           PostgreSQL (013/014)
                           finish-material classification · robot thresholds · assessment
                                    │
                           dump.sql │
                                    ▼
                                  to_ifc ──▶ .ifc ──▶ verify_ifc
```

## Why Line Weight?

In LH (Korea Land and Housing Corporation) drawing sets, the **area-calculation basis drawing** draws room
boundaries with heavy lines (1.42pt) and furniture, fixtures, and hatching with thin lines (0.24pt). Filtering by
line weight leaves only the room boundaries. Snapping the remaining line segments into axis alignment and
converting them into polygons yields the room areas, which are then verified by **comparing them against the
area schedule printed on the drawing**.

Result for the LH Type 26 unit: the areas of all 7 faces are **within 0.0025%** of the values shown on the
drawing (even after rounding to whole millimeters).

## Thickness (THK) and Level (FL) Are Different Values

The `THK` column in the interior finish schedule is **thickness**; the finished-surface level of each room is
given separately, in the `FL`/`SL` labels on the partial detail drawing. In the bathroom, the slab is dropped by
150mm, so its thickness is the greatest (180) while its finished surface is the lowest (FL+30). Reading THK as a
level **inverts the direction of the height difference.**

The two drawings verify each other: `FL − SL == THK` (for all 5 rooms).

## Principles Followed When Exporting to IFC

We do not invent values that are not on the drawings. That principle changes which IFC structures are chosen.

| Situation | Handling |
|---|---|
| Area | The drawing's area-schedule value goes into `Qto_SpaceBaseQuantities`; it is not recomputed from the polygon |
| Layer thicknesses inconsistent with the total thickness | Instead of `IfcMaterialLayerSet` (asserts thicknesses), `IfcMaterialConstituentSet` (does not) |
| Effective clear width | Only the **upper limit at the inside of the door frame** goes into `IfcDoor.OverallWidth`; `ClearWidthKnown=false` |
| Ceiling height not stated | Extruded to a nominal value, but with `HeightIsNominal=true` |
| Contradictions in the original text (bathroom and balcony levels) | Not resolved; both sides preserved in `ConflictNote` |
| Rooms with no face on the drawings | Registered without geometry + `EvidenceBasis='inferred'` |

## Usage

```bash
python bim/to_ifc.py        # dump.json → bim/LH_26*.ifc (IFC4 model of the LH Type 26 unit)
python bim/verify_ifc.py    # reads the generated IFC back and verifies it (exit 1 on failure)
```

`dump.json` is generated by running `dump.sql` against the database. `verify_ifc.py` does not use the generation
script's variables and reads **only from the file** — it triangulates the geometry to recompute the areas and
compares them against the values shown on the drawing.

## Tests

```bash
python -m pytest bim/tests/ -q
```

The drawing PDF is not in the repository because `data/` is gitignored. Without it, the drawing-dependent tests
are skipped and only the pure-geometry tests run.

The expected values come not from synthetic fixtures but from **the area schedule printed on the drawing**.
Mutation testing confirmed that the tests are load-bearing (all 10 mutations blocked: line weight, snap
tolerance, hole rings, coordinate flip, scale, face selection, FL sign, and diagonal-line exclusion; the
unmutated control passed).

## Limitations

1. **Verified against only one drawing.** For drawings from other issuing agencies, `BOUNDARY_WIDTH_PT` has to be re-tuned.
2. **The bathroom doorway width is not on the drawings.** The doorway is included in the system bathroom (prefab pod) product, so it is not part of the window-and-door procurement.
3. **The effective clear width is not determined for any opening.** A door-frame section detail or a post-construction field measurement is needed.
4. **The contradiction in the original text about the bathroom and balcony levels is unresolved.** It needs to be settled later; for the balcony, the balcony↔outdoor-unit room assessment flips depending on
   which branch is chosen.
