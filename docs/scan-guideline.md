## 1. 가장 먼저 읽을 것: 스캔 품질이 판정 결과를 결정한다

이 시스템에서 **스캔 노이즈는 그대로 "바닥 결함"으로 계상된다.** 직선자 시뮬레이션이 상부 볼록
포락선 아래 **최대** 틈새를 취하기 때문에`[구현: core/straightedge.py]`, 무작위 노이즈의 아래쪽
꼬리가 곧바로 편차로 읽힌다. 평균이 아니라 최악값을 보는 구조이므로 노이즈는 상쇄되지 않는다.

### 1.1 실측 근거 (결함이 전혀 없는 완전 평탄면)

8m x 6m 합성 평탄 바닥(점 간격 2cm, 결함 0개)에 **노이즈만** 주입하고 분석한 결과다`[실측]`.
기준은 `floor-kcs-exposed`(3m당 7mm, U=5mm), 판정 셀 48개.

| 주입 노이즈 (표준편차) | 측정된 최대 편차 | 측정된 평균 편차 | 판정 결과 (적합/경계/보수/재시공) |
|---|---|---|---|
| 0 mm | 0.00 mm | 0.00 mm | **48** / 0 / 0 / 0 |
| 0.5 mm | 1.52 mm | 1.35 mm | **48** / 0 / 0 / 0 |
| 1.0 mm | 3.04 mm | 2.71 mm | 0 / **48** / 0 / 0 |
| 2.0 mm | 6.07 mm | 5.41 mm | 0 / **48** / 0 / 0 |
| 3.0 mm | 9.11 mm | 8.11 mm | 0 / **48** / 0 / 0 |

**결함이 하나도 없는 완벽한 평면인데도 노이즈 1mm에서 이미 전 셀이 "경계"가 된다.**

이 표에서 읽어야 할 관계`[실측]`:

- 측정된 최대 편차 ≈ **노이즈 표준편차 x 3.0** (표의 네 행 모두 배율 3.03~3.04로 일정)
- 측정된 평균 편차 ≈ 노이즈 표준편차 x 2.7
- 위 배율은 **점 간격 2cm / 서브셀 5cm** 조건에서의 값이다. 점이 성기면 서브셀 중앙값의 노이즈
  억제 효과가 줄어 배율이 더 커진다`[추정]`

### 1.2 실측 근거 (진짜 결함이 노이즈에 묻히는 과정)

같은 8m x 6m 바닥 한가운데에 **12mm 함몰**을 넣고 노이즈만 바꾼 결과다`[실측]`.

| 조건 | 측정된 최대 편차 | 판정 결과 (적합/경계/보수/재시공) |
|---|---|---|
| 노이즈 0 | 11.48 mm (정답 12mm) | 36 / 12 / 0 / 0 |
| 노이즈 표준편차 2mm | 15.47 mm | 0 / **44** / **4** / 0 |

노이즈가 없으면 12mm 함몰을 11.48mm로 잡아내고 결함 주변 12개 셀만 경계로 표시한다. 노이즈를
넣으면 **결함이 없는 44개 셀까지 경계·보수로 오염되고**, 최대값도 15.47mm로 부풀어 실제보다
나쁜 결과가 나온다. 즉 노이즈는 결함을 가리는 것이 아니라 **없는 결함을 만들어낸다.**

> 이 현상은 백로그 티켓 35로 기록되어 있으며, 위 판정 분포(36/12 및 0/44/4)는 티켓의 기록과
> 정확히 일치함을 재현으로 확인했다`[실측]`. 최대값이 티켓 기록(11.71mm / 14.86mm)과 소수점
> 단위로 다른 것은 원 데모의 함몰 반경이 기록되지 않아 재현 시 반경을 달리 잡았기 때문이다.

### 1.3 그래서 현장에서 해야 할 일

모바일 LiDAR의 점군 노이즈는 장비 성능만이 아니라 **스캔 방법**에 크게 좌우된다`[추정]`. 아래
2~7장은 전부 "노이즈와 드리프트를 줄이는 방법"이라는 하나의 목적을 위한 것이다.

참고로 문헌 조사값`[문헌, 스펙 §1.3]`: iPhone LiDAR의 상대 거리 오차는 방 규모에서 약 3cm,
수직 방향은 ±7mm 수준, SLAM 드리프트는 이동거리의 1~2%다. 시방서 허용오차(3m당 3~10mm)와
같은 자릿수이거나 이를 초과한다. **이 프로젝트가 직접 측정한 값이 아니다.**

## 2. 스캔 전 준비

### 2.1 조명

- 밝고 균일한 조명을 확보한다. LiDAR 자체는 적외선이라 어둠에서도 거리를 재지만, iPhone/iPad
  앱은 대부분 카메라 영상으로 SLAM 추적(자기 위치 추정)을 하므로 **어두우면 추적이 흔들려
  드리프트가 커진다**`[추정]`
- 직사광선이 바닥에 강하게 들어오는 시간대는 피한다. 노출 차이로 추적이 끊기기 쉽다`[추정]`
- 조명이 켜져 있는지 확인하고, 스캔 도중 자동 소등되지 않게 한다`[추정]`

### 2.2 장애물 정리

- 판정 대상 바닥에서 **자재·공구·박스를 치운다.** 가려진 바닥은 판정 불가로 빠지고, 인식률
  (coverage)이 70% 아래로 떨어지면 `low_coverage` 경고가 뜬다`[구현]`
- 치울 수 없는 고정 설비는 그대로 두고 스캔한다. 엔진이 구역 단위로 처리하므로 설비 주변만
  판정에서 빠진다`[구현: core/zones.py]`
- **주 바닥면보다 0.3m를 초과해 높고 면적 3m² 이하인 평면은 "가구 상판"으로 자동 제외된다**
  `[구현: core/zones.py furniture_gap_m=0.3]`. 조건이 "초과"이므로 정확히 0.3m 차이면 제외되지 않는다.
  판정하려는 단(壇)이 이 조건에 걸리면 결과에서 빠지므로, 이런 면을 판정해야 한다면 별도
  측정위치로 나눠 스캔한다

### 2.3 기준점과 측정 범위

- 스캔 시작·종료 지점을 같은 곳으로 잡는다(폐루프)`[스펙 §1.3]`. 시작점으로 돌아오면 앱이
  누적 드리프트를 보정할 여지가 생긴다`[추정]`
- 한 번에 담을 범위를 미리 정한다. 넓은 공간을 한 번에 훑기보다 **구역을 나눠 여러 번 스캔**
  하는 편이 드리프트가 적다`[스펙 §1.3]`
- 판정에는 **약 1m의 연속 직선 구간**이 필요하다. 1m에 크게 못 미치는 폭의 통로·틈새는 구조적
  으로 판정 불가다`[구현: min_span_m=1.0]`. 정확한 조건은 "실측 라인 길이 L + 서브셀 한 스텝
  >= 1.0m"이므로, 축 방향(스텝 5cm)에서는 L이 0.95m부터, 대각 방향(스텝 약 7.07cm)에서는
  약 0.93m부터 통과한다`[구현: cells.py, 이산화 여유 한 스텝 허용 - 백로그 티켓 2 해소분]`
- 3m 기준을 온전히 적용하려면 3m 연속 구간이 필요하다. 3m가 안 되면 확보된 길이 L로 허용치를
  `pass x L / 3`으로 축소 환산해 판정하고 `reduced_span` 경고가 붙는다`[스펙 §4.2]`

## 3. 스캔 절차

아래 수치 중 `[구현]` 표시가 없는 것은 실무 권고이며 이 프로젝트가 검증하지 않았다.

### 3.1 이동 경로

- **폐루프**: 시작점으로 돌아와 종료한다`[스펙 §1.3]`
- **바닥-벽-천장 교차 경로**: 바닥만 훑지 말고 벽과의 접합부를 함께 지나간다`[스펙 §1.3]`.
  평면이 여러 방향으로 잡히면 SLAM이 자세를 안정적으로 고정한다`[추정]`
- 급격한 방향 전환·회전을 피한다. 추적을 놓치는 가장 흔한 원인이다`[추정]`
- 같은 경로를 두 번 지나며 겹치게 훑는다`[추정]`

### 3.2 측정 거리와 높이

- **센서에서 대상면까지 0.3m ~ 1.5m를 유지한다**`[스펙 §1.3]`. 이보다 멀면 점이 성겨지고
  정밀도가 떨어진다
- 바닥 스캔 시 기기를 허리 높이 이하로 낮추고 바닥을 내려다보는 각도로 잡는다`[추정]`
- 대상면에 대해 가능한 한 수직에 가깝게 겨눈다. 비스듬히 스치면 같은 면적에서 얻는 점이
  줄고 거리 오차가 커진다`[추정]`

### 3.3 속도

- **천천히 걷는 속도 이하**로 이동한다`[추정]`
- 결함이 의심되는 구간에서는 멈춰서 잠시 머문다. 같은 지점을 여러 번 관측하면 서브셀 중앙값이
  안정된다`[구현: 서브셀당 점이 많을수록 중앙값이 노이즈에 강건]`

### 3.4 점 밀도 (판정 가능 여부를 직접 좌우함)

엔진은 5cm x 5cm 서브셀 단위로 점을 모아 중앙값을 대표 높이로 쓴다. **서브셀 하나에 점이 3개
미만이면 그 서브셀은 버려진다**`[구현: subcell.py min_points=3]`.

- 5cm 칸에 점 3개를 채우려면 **점 간격이 약 2.9cm보다 촘촘해야 한다**`[구현에서 계산]`
- 실무 목표는 **점 간격 2cm 이하**로 잡는다. 위 1.1절 실측이 이 조건에서 얻은 값이다`[실측]`
- 판정 셀(1m x 1m)은 **유효 서브셀이 70% 이상**이어야 판정된다`[구현: min_occupancy=0.7]`
- 3m 직선자 창도 마찬가지로 **예상 표본의 70% 이상**이 있어야 그 방향을 평가한다`[구현: cells.py]`.
  예상 표본 수는 방향에 따라 다르다: **축 방향**(0/90도, 스텝 5cm)은 61개 중 43개 이상,
  **대각 방향**(45/135도, 스텝 약 7.07cm)은 43개 중 31개 이상이다. 중간에 넓게 비면 그 방향은
  조용히 건너뛴다

## 4. 바닥면 스캔 요령

- 방 전체를 **지그재그(보스트로페돈) 경로**로 빠짐없이 훑는다`[추정]`
- 벽에서 시작해 벽으로 끝낸다. 바닥 가장자리가 잘리면 그 셀은 판정에서 빠진다`[추정]`
- **단차·경사가 있는 바닥**: 엔진이 높이 밴드로 구역을 나눈 뒤 평면을 추종하며 영역을
  성장시키므로 설계 구배가 있어도 처리된다`[구현: core/zones.py grow]`. 다만 구역 하나가
  **1m² 미만이면 파편으로 버려지므로**`[구현: min_area_m2=1.0]`, 좁은 단은 판정되지 않는다
- **한 측정위치는 한 파일로 스캔하는 것이 기본이다.** 같은 측정위치에 여러 파일을 그냥 올리면
  파일마다 별도 분석이 되어 판정도 따로 나온다`[구현]`
- **다만 이것이 더 이상 절대적 제약은 아니다.** 부득이하게 나눠 찍었다면 대시보드의 정합 화면에서
  두 바닥 스캔을 대응점으로 맞춰 **병합 스캔 하나로 합칠 수 있다**
  `[구현: dashboard/components/registration/registration-workbench.tsx]`. 절차와 한계는 9장에 있다.
  **그래도 기본 권고는 여전히 한 파일이다** - 정합에는 사람이 두 그림에서 같은 지점을 찍는 수작업이
  필요하고, 그 결과의 **수평 방향 정확도를 시스템이 보증하지 못하기** 때문이다(9.5절)

## 5. 벽면 스캔 요령

벽면은 바닥보다 검출 조건이 까다롭다. 아래 조건을 못 맞추면 그 벽은 통째로 `wall_{n}_skipped`
경고와 함께 결과에서 빠진다`[구현: core/walls.py]`.

- **벽 높이 0.8m 이상**이 연속으로 잡혀야 벽 후보가 된다`[구현: min_height_m=0.8]`
- **벽 길이 1.0m 이상**이어야 한다`[구현: min_length_m=1.0]`
- 벽면 중간 높이가 실제로 스캔되어야 한다. 바닥과 천장만 찍히고 중간이 비면 벽으로 인정되지
  않는다`[구현: cnt_mid 조건]`. **벽을 정면에서 위아래로 훑어야 한다**
- **바닥 접합부와 천장 접합부 각 10cm는 판정에서 자동 제외된다**`[구현: edge_margin_m=0.1]`.
  실물 벽 검측도 접합부를 제외하므로 의도된 동작이며, 걸레받이 부근을 판정하려 애쓸 필요 없다
- 한 번에 판정되는 벽은 **최대 8개**다`[구현: max_walls=8]`
- **수직도(plumbness)는 스캔 좌표계의 z축 기준 상대값이며 중력 기준 절대값이 아니다**
  `[구현: 항상 plumbness_relative_to_z 경고]`. 기기가 기울어진 상태로 좌표계가 잡히면 벽
  전체가 기울어진 것으로 읽힌다. 스캔 시작 시 기기를 수평·수직으로 안정시키고 시작한다`[추정]`

## 6. 피해야 할 상황

| 상황 | 왜 문제인가 | 대응 |
|---|---|---|
| **거울·유리·광택 타일** | LiDAR가 반사면 너머에 허상 점을 만든다 | 반사면을 시야에서 빼거나, 그 구역을 판정 대상에서 제외한다`[추정]` |
| **젖은 바닥·물웅덩이** | 경면 반사로 점이 아예 안 잡히거나 튄다 | 마른 뒤 스캔한다`[추정]` |
| **사람·장비의 이동** | 움직이는 물체가 바닥 위 허상층으로 남는다 | 스캔 중 대상 구역에 아무도 들어오지 않게 한다`[추정]` |
| **같은 곳을 왕복하며 위치가 어긋남** | 이중 표면(유령층)이 생긴다. 엔진이 서브셀 높이 분포의 쌍봉성으로 감지한다. 판정 조건은 **세 가지를 모두** 만족할 때다`[구현: subcell.py]`: ① 서브셀에 점이 **4개 이상**, ② 정렬한 높이값의 최대 간극이 **8mm 초과**(`bimodal_gap_m=0.008`), ③ 간극을 경계로 **양쪽 점 수가 각각 전체의 30% 이상**(`bimodal_min_frac=0.3`). 조건을 만족하면 그 서브셀을 버린다 | 추적이 끊긴 것을 알아채면 그 자리에서 다시 스캔한다 |
| **넓고 특징 없는 면만 훑기** | SLAM이 참조할 특징이 없어 드리프트가 누적된다 | 벽·기둥·모서리를 시야에 포함시킨다`[추정]` |
| **한 번에 너무 넓은 범위** | 드리프트가 이동거리에 비례해 누적된다`[문헌]` | 구역을 나눠 여러 번 스캔한다`[스펙 §1.3]` |
| **융합 메시(fused mesh) 내보내기** | 앱이 표면을 매끄럽게 다듬어 **실제보다 양호한 결과**가 나온다 | 가능하면 원시 점군으로 내보낸다. 불가피하면 업로드 시 계보를 "융합 메시"로 **직접** 선택한다. 그러면 분석 결과와 보고서에 `fused_mesh_smoothed` 경고가 표시된다`[구현: worker/flatworker/lineage.py]`. **시스템은 융합 메시를 자동으로 감지하지 못한다**`[스펙 §5.1.1 계획, 미구현]` |
| **천장 포함 스캔** | 과거에 팬텀 벽이 검출되는 문제가 있었다 | 현재는 중간 대역 점유 조건으로 해소되어 있다`[구현: 티켓 24 해결]`. 천장이 들어가도 무방하다 |

## 7. 파일 저장과 전송

### 7.1 지원 포맷

업로드 가능한 확장자는 다음 7종이다`[구현: engine/flatness/io/reader.py, dashboard/lib/upload/validate.ts]`.

| 확장자 | 종류 | 비고 |
|---|---|---|
| `.ply` | 점군 (바이너리/ASCII) | 가장 권장. **면(face) 요소는 읽지 않고 버린다** |
| `.las` / `.laz` | 점군 (LAS/LAZ) | 지상 레이저 스캐너(TLS) 데이터도 동일 처리 |
| `.pts` | 점군 (ASCII) | 첫 줄의 점 개수 행은 자동으로 건너뜀 |
| `.xyz` / `.txt` / `.csv` | 텍스트 점군 | **앞 3열을 x, y, z로 해석한다.** 공백·쉼표 구분 모두 인식 |

- **E57은 지원하지 않는다**`[스펙 §2.2]`. 현재 사용 장비가 내보내지 않는 포맷이라 후속 과제로
  이관되어 있다
- 텍스트 포맷에서 숫자 3개를 만들 수 없는 행(헤더·주석·빈 줄)과 `nan`/`inf` 행은 자동으로
  건너뛴다`[구현: text_reader.py]`
- 소수점을 쉼표로 쓰는 로케일(예: `1,5`)은 **조용히 잘못 파싱될 수 있다**`[백로그 티켓 15의
  미해소 부분]`. 티켓 15는 `[해결: P1d]`로 표기되어 있으나 해결된 것은 `nan`/`inf` 행 필터링
  부분이고, **쉼표 소수점 로케일 대응은 여전히 미해소다.** 내보내기 설정에서 소수점이
  마침표인지 확인한다

### 7.2 업로드 제약

- **파일당 50MB 상한**`[구현: MAX_UPLOAD_BYTES, Supabase Storage Free 티어 한도]`. 초과하면
  업로드가 대시보드에서 그대로 거부된다
- 성능 참고`[실측]`: 3천만 점 파일을 분석 엔진에 **직접** 넣어(대시보드 업로드 경로를 거치지
  않고 개발 PC에서 엔진을 직접 호출해) 처리하는 데 **30.2초, 피크 메모리 증가 1.31 GiB**가
  걸렸다(허용 게이트는 300초·2 GiB). 처리 시간은 재실행마다 30~40초 범위로 변동한다.
  **다만 이 시험에 쓴 파일 자체가 이미 50MB 상한을 크게 웃돈다** - 같은 시험의 점당 약
  12바이트 계산을 적용하면 3천만 점은 약 360MB다(`docs/service-report.md` 5.3절). 즉 엔진의
  처리 속도는 빠르지만, **이 정도 규모의 파일은 현재 대시보드로는 애초에 올릴 수 없다**
- **다만 그 파일은 권장 밀도의 스캔이 아니다.** 위 성능 시험은 점 간격 약 4.5mm로, 이 문서가
  실측으로 검증한 조건인 2cm(1.1절)보다 **약 20배 촘촘하다**(면적당 점 수 기준). 같은
  30m x 20m(600 m²) 바닥을 **점 간격 2cm로 스캔하면 약 150만 점, 점당 12바이트 기준 약 18MB**이고,
  판정 가능 최소 밀도인 2.9cm(3.4절)면 약 8.6MB다`[구현에서 계산]`. **권장 밀도를 지키면 상당히
  넓은 공간도 50MB 안에 들어온다.** 상한에 걸린다면 대개 공간이 넓어서가 아니라 점 간격이
  필요 이상으로 촘촘해서다
- **그래도 50MB를 넘을 때 맞추는 방법**:
  - **스캔 범위를 나눠 여러 측정위치로 올린다.** 넓은 공간을 한 파일에 담으려 하지 말고,
    처음부터 구역을 나눠 여러 번 스캔한다 - 2.3절이 드리프트 억제를 위해 이미 권고하는
    방법과 같다. 다만 **측정위치 하나에 여러 파일을 그냥 올리면 각각 별도 분석이 되어 판정이
    따로 나온다**`[구현: 4장]`. 그러므로 구역별로 **측정위치 이름 자체를
    다르게** 매겨 올린다(예: "1층 로비-A구역"/"1층 로비-B구역", 7.3절). 구역 경계는 스캔
    시작 전에 미리 정해 둔다(2.3절)
  - **구역을 나눴는데도 하나의 판정이 필요하다면** 두 바닥 스캔을 정합해 병합 스캔으로 합칠 수
    있다(9장). 다만 정합은 대응점 수작업이 필요하고 수평 방향 보장이 약하므로, **판정 단위를
    나눠도 되는 상황이면 위처럼 측정위치를 나누는 편이 낫다**`[추정]`
  - **점 간격을 필요 이상으로 촘촘하게 잡지 않는다.** 파일 크기는 점 개수에 거의 비례해서
    커진다(위 360MB 계산이 그 예다). 이 문서가 실측으로 정확도를 검증한 조건은 점 간격
    **2cm**이며(1.1절), 그보다 훨씬 촘촘한 스캔(예: 위 성능 시험의 약 4.5mm)이 정확도를
    추가로 개선한다는 근거는 이 문서에 없다. 판정 가능 최소 조건인 3.4절의 밀도(약
    2.9cm보다 촘촘함)만 지키면 충분하며, 3.1절의 왕복 훑기·3.3절의 정지 관찰은 결함이
    의심되는 구간에 한정하고 바닥 전체에 불필요하게 반복 적용하지 않는다`[추정]`

### 7.3 업로드 시 함께 입력할 정보

업로드 화면에서 아래를 정확히 입력한다. 이 값들은 판정 결과와 보고서에 그대로 박제된다`[스펙 §6.1]`.

- 측정위치(현장/동/층/공간)
- 표면 유형(바닥/벽면)
- 측정일자, 담당자, 장비
- **데이터 계보**(원시 점군 / 융합 메시 / 모름). **자동 감지되지 않으므로 반드시 직접 선택한다**
  `[스펙 §5.1.1은 PLY face 요소에 의한 자동 감지를 계획했으나 미구현]`. 여기서 잘못 고르면
  융합 메시로 스무딩된 결과에 경고 없이 "원시 점군" 표기가 붙는다. 반대로 제대로 고르면
  분석 결과 화면과 보고서에 경고가 실린다`[구현: worker/flatworker/lineage.py]`
- **적용 판정 기준** (기본값이 선택되어 있으나 현장 조건에 맞는지 확인한다.
  기준별 근거는 [`criteria-sources.md`](criteria-sources.md) 참고)

## 8. 단위 확인 절차의 의미

업로드 직후 시스템은 **단위를 자동 확정하지 않고 사용자에게 묻는다**`[스펙 §5.1.1]`. 귀찮아
보이지만 이 절차를 대충 넘기면 결과 전체가 무의미해진다.

**왜 자동 확정하지 않는가**: 점군 파일에는 좌표 단위가 기록되지 않는 경우가 많다. 엔진은
바운딩 박스의 수평 범위만 보고 후보를 제시할 수 있는데`[구현: io/units.py]`,

| 파일상 수평 범위 | 추정 | 신뢰도 |
|---|---|---|
| **1 미만** | cm / m / mm 3후보 | **전부 낮음 (모호 구간)** |
| 1 ~ 200 | m(미터) | 높음 |
| **200 초과 ~ 1,000 미만** | cm / m / mm 3후보 | **전부 낮음 (모호 구간)** |
| 1,000 ~ 200,000 | mm(밀리미터) | 높음 |
| **200,000 초과** | cm / m / mm 3후보 | **전부 낮음 (모호 구간)** |

200~1000 구간은 "2~10m 방을 cm로 쓴 것"일 수도 "200~1000m 대형 현장을 m로 쓴 것"일 수도 있어
기계적으로 구분할 수 없다. 어느 구간에도 들지 않는 값(1 미만, 20만 초과)도 같은 3후보 낮음
처리로 떨어진다.

> **위 추정표는 CLI(`flatness analyze`)를 `--units` 없이 실행했을 때 콘솔에 출력되는 내용이다.**
> 대시보드 업로드 경로에서는 이 후보·근거가 화면에 표시되지 않는다(아래 참고).

**틀리면 어떻게 되는가**: 단위를 1000배 틀리면 mm 단위 편차도 1000배로 계산된다. 7mm 허용치
기준에서 실제로는 적합한 바닥이 전 구간 재시공으로 나오거나, 반대로 심각한 결함이 0.007mm로
읽혀 전 구간 적합으로 나온다. **경고 없이 조용히 틀린 답이 나온다.**

**확인 방법**: **스캔 앱의 내보내기 설정에서 단위를 직접 확인하는 것이 가장 확실한 방법이다.**
대시보드에서는 아래의 높이 뷰 축 눈금을 실제 공간 크기와 대조해 한 번 더 확인한다.

**대시보드가 보여주는 것 - 높이 뷰(평면도)**: 단위 확인 화면은 파일명과 단위 선택지(m/cm/mm)
옆에 **사전 검사가 만든 높이 뷰 PNG를 함께 표시한다**`[구현: dashboard/components/unit-confirm-form.tsx]`.
위에서 내려다본 점군 그림이고, **축 눈금이 곧 파일 단위 수평 범위**다(축 라벨이
`X (파일 단위)` / `Y (파일 단위)`)`[구현: engine/flatness/outputs/height_view.py render_height_view]`.
화면 안내도 같은 말을 한다 - "축 눈금은 미터가 아니라 파일 단위이므로, 눈금이 가리키는 크기와
실제 공간 크기를 견주어 단위를 고르세요. 예를 들어 8m짜리 방인데 눈금이 8000까지 간다면
mm입니다."`[구현: unit-confirm-form.tsx]`

- 눈금이 작아 읽기 어려우면 그림 아래 **"원본 크기로 열기 (새 탭)"** 링크로 원본을 연다`[구현]`
- **점이 성겨 색이 거의 없거나 "유효 데이터 없음 - 점 밀도 부족"이 찍힌 그림이어도 축 눈금은
  유효하다**`[구현: height_view.py, unit-confirm-form.tsx 안내 문구]`. 색이 아니라 눈금을 본다
- 확정 버튼은 **"단위 확정 후 분석 시작"** 이다`[구현]`

> **그래도 후보·신뢰도는 여전히 화면에 없다.** 위 추정표(`detect_units`의 3후보와 신뢰도)는
> **대시보드 어디에도 표시되지 않는다**`[구현: unit-confirm-form.tsx - 단위 후보를 저장할 컬럼이 없어 후보·근거 표시는 백로그]`.
> 화면에 있는 것은 **그림의 축 눈금뿐**이고,
> "cm/m/mm 중 무엇이 유력한가"라는 시스템의 판단은 보이지 않는다. 후보 목록을 수치로 보고
> 싶다면 CLI를 `--units` 없이 한 번 실행한다.
>
> **그림이 아예 없는 경우도 있다.** ① 사전 검사를 돌지 않은 스캔(외부 결과 임포트 등)은
> 높이 뷰 자체가 없어 **예전처럼 파일명과 선택지만 있는 화면**이 뜬다. ② 그림은 만들어졌으나
> 불러오지 못하면 **"높이 뷰를 불러오지 못했습니다. 그림 없이도 단위는 확정할 수 있습니다."**
> 안내가 대신 뜬다`[구현: unit-confirm-form.tsx]`. 두 경우 모두 **스캔 앱의 내보내기 설정을
> 확인하는 것 말고는 대조할 근거가 없다.**

## 9. 측정위치를 나눠 스캔했을 때(정합)

한 측정위치를 부득이하게 두 파일로 나눠 찍었다면, 대시보드의 **정합** 기능으로 두 스캔을 하나의
**병합 스캔**으로 합칠 수 있다`[스펙(구배·정합) §6.2]`. 이 장은 그 절차와 **어디까지 믿을 수 있는지**를 다룬다.

### 9.1 언제 쓰나

- **기본은 여전히 한 파일이다**(4장). 정합은 사람이 두 그림에서 같은 지점을 찍는 수작업이고,
  9.5절이 밝히듯 **수평 방향 정확도를 시스템이 보증하지 못한다**
- 정합을 쓸 상황은 둘이다`[추정]`: **공간이 너무 커서 한 번에 못 찍을 때**, 그리고 **기둥·설비에
  가려 한 파일로는 인식률(coverage)이 안 나올 때**(2.2절)
- 판정을 구역별로 나눠도 되는 상황이면 정합 대신 **측정위치 자체를 나누는 편이 낫다**(7.2절)`[추정]`

**정합할 수 있는 스캔의 조건**`[구현: dashboard/app/registrations/new/page.tsx]`:

| 조건 | 이유 |
|---|---|
| **바닥 스캔만** | 벽 스캔은 높이 뷰가 가느다란 띠라 대응점 클릭이 성립하지 않는다`[구현: 같은 파일]` |
| **같은 측정위치에 올라가 있을 것** | 정합 진입점이 측정위치 단위다 |
| **사전 검사가 끝나 높이 뷰가 있을 것** | 대응점을 찍을 그림과 좌표 정보가 필요하다 |
| **단위가 확정된 "분석 준비됨" 상태** | 워커가 "스캔의 단위가 확정되지 않아 정합할 수 없습니다."로 거부한다`[구현: worker/flatworker/registration.py]` |

조건을 만족하는 스캔이 2개 미만이면 화면이 **"정합할 수 있는 스캔이 두 개 이상 필요합니다."**
라고 안내한다`[구현]`.

2. 측정위치 목록에서 그 측정위치의 **"스캔 정합"** 을 누른다`[구현: dashboard/components/location-tree.tsx]`
3. **"스캔 정합 시작"** 화면에서 두 스캔을 고른다`[구현: dashboard/app/registrations/new/page.tsx]`.
   **"기준 스캔 (A) - 이 스캔의 좌표계를 유지합니다"** 와 **"맞출 스캔 (B) - A에 맞춰 회전·이동합니다"**
   다`[구현: registration-create-form.tsx]`. **더 넓거나 더 잘 찍힌 쪽을 A로** 고르는 편이 좋다`[추정]`.

   **번갈아** 클릭하면 한 쌍이 된다. 잘못 찍은 쌍은 목록에서 **"지우기"** 로 뺀다`[구현: registration-workbench.tsx]`

6. 결과 화면에서 **"정합 잔차 RMSE" / "ICP 반복" / "겹친 영역(추정)"** 수치와
   **"겹쳐보기 (정합 결과 육안 확인)"** 그림을 확인한다`[구현: registration-workbench.tsx]`

   가 활성화된다`[구현: 같은 파일]`

   버튼 라벨은 분석 종류에 따라 "평활도 분석" 또는 "구배 분석"으로 만들어진다

### 9.3 대응점 찍는 요령 (이 장에서 가장 중요하다)

**최소 3쌍**이어야 정합을 실행할 수 있다`[구현: dashboard/lib/domain/registration.ts MIN_CORRESPONDENCES=3,
engine/flatness/core/registration.py register_clouds]`. 화면 안내는 **"최소 3쌍이 필요하고 4쌍 이상을
권장합니다."** 다`[구현: registration-workbench.tsx]`.

**이 문서는 8쌍 이상을 권한다**`[추정]`. 근거는 엔진의 회전 불확도 식이다. 회전 불확도
`σ_θ ≈ σ_click / sv1`이고 `sv1 = (대응점의 측방 RMS 편차) × √N`이므로, **점을 더 찍는 것과 더 벌려
찍는 것이 둘 다 같은 방향으로 듣는다**`[구현: engine/flatness/core/registration.py correspondence_geometry]`.
같은 지그재그 배치에서 잰 `sv1` 값이다`[실측]`.

| 대응점 수 N | sv1 |
|---|---|
| 3 | 0.0817 |
| 6 | 0.1172 |
| 10 | 0.1557 |
| 20 | 0.2228 |

3쌍에서 10쌍으로 늘리면 `sv1`이 약 1.9배가 되고 회전 불확도는 그만큼 줄어든다. 8쌍이라는 숫자
자체는 이 표에서 직접 측정한 값이 아니라 **√N 관계에서 실무적으로 잡은 선이다**`[추정]`.

**넓게 분산해 찍는다.** 한곳에 몰리거나 일직선이면 **시스템이 거부한다.** 실제 거부 문구는
셋이다`[구현: engine/flatness/core/registration.py check_correspondence_geometry]`.

| 거부 문구 | 게이트 |
|---|---|
| "…이 한 직선 위에 있습니다(공선). 회전을 정할 수 없습니다. 일직선을 벗어난 지점을 포함하거나 대응점을 더 찍으세요." | 회전 불확도 60도 초과이면서 공선으로 판별된 경우 |
| "…이 한곳에 몰려 있습니다(회전 불확도 N도). 서로 멀리 떨어진 지점을 고르거나 대응점을 더 찍으세요." | 회전 불확도 **60도 초과**`[구현: MAX_CORR_ROTATION_SIGMA_RAD]` |
| "…이 정합 영역의 좁은 구역에만 몰려 있습니다(퍼짐 X m가 영역 Y m의 Z%). 회전 오차가 영역 전체로 확대됩니다. 정합 영역 전체에 넓게 분산해 찍으세요." | 최대 퍼짐이 정합 영역 대각의 **12% 미만**`[구현: MIN_CORR_SPREAD_FRACTION=0.12]` |

> **문구 앞의 "…" 자리에 들어가는 말은 검사 시점에 따라 다르다.** 원본 파일을 읽기 전에 도는
> 조기 검사는 **"첫 번째 스캔에서 찍은 대응점"** / **"두 번째 스캔에서 찍은 대응점"** 으로,
> 점군을 읽은 뒤 엔진 안에서 도는 검사는 **"대응점"** 으로 나온다
> `[구현: worker/flatworker/registration.py, engine/flatness/core/registration.py]`. 세 번째 줄의
> 퍼짐 검사는 점군의 범위를 알아야 하므로 **조기 검사에서는 돌지 않고** 정합 실행 뒤에 나온다
> `[구현: worker가 region_diag_m=0.0으로 건너뛴다]`.

즉 **개수만 채우면 되는 것이 아니다.** 두 번째·세 번째 게이트는 "몇 개를 찍었는가"가 아니라
"얼마나 벌려 찍었는가"를 본다.

나머지 요령:

- **두 스캔에서 물리적으로 같은 지점을 찍어야 한다.** 모서리, 기둥 밑동, 배수구, 바닥 이음매처럼
  두 그림 모두에서 위치를 특정할 수 있는 곳을 고른다`[추정]`
- **색이 없는(회색) 칸은 쓸 수 없다.** 클릭하면 "그 지점은 높이 값이 없어(점이 성겨 서브셀이
  비었습니다) 대응점으로 쓸 수 없습니다. 색이 칠해진 곳을 고르세요."가 뜬다
  `[구현: dashboard/components/registration/point-picker.tsx]`
- 화면 안내도 같은 취지다 - **"쌍은 서로 1m 넘게 떨어뜨리고 한 직선 위에 놓이지 않게 넓게 흩어
  고르세요."**`[구현: registration-workbench.tsx]`

**정성껏 찍어도 잔차는 남는다.** 합성 픽스처로 잰 정합 복원 정확도다`[실측]`.

| 조건 | 회전 오차 | 면내(수평) 오차 | z 오차 |
|---|---|---|---|
| 클릭 오차 0 (이상적 조건) | 0.00066도 | 0.126mm | - |
| **노이즈 1mm + 클릭 ±5cm (현실 조건)** | **0.41283도** | **44.656mm** | **0.0080mm** |
| 위와 같은 조건에서 ICP 전(초기 정렬만) | 0.46214도 | 51.720mm | -0.261mm |

**ICP는 면내 오차를 14%만 줄이고 z만 33배 개선한다.** 즉 **수평 오차는 대응점을 찍는 순간
대부분 결정되고 나중에 회복되지 않는다.** 원 설계가 기대한 "ICP가 클릭 오차를 회복한다"는
가정은 **z 방향에 대해서만 참이다**`[실측]`.

### 9.4 넓은 현장은 구역을 나눠 찍어라

**대응점 클릭 정밀도는 현장 크기에 반비례한다.** 대응점 좌표는 높이 뷰 격자의 셀 중심으로
양자화되는데, 그 **셀 크기가 `현장 긴 변 / 256`** 이기 때문이다
`[구현: engine/flatness/outputs/height_view.py _TARGET_LONG_SIDE=256·subcell_m_for_bbox,
dashboard/lib/domain/height-view.ts pixelToWorld]`.

| 현장 긴 변 | 셀 크기(= 클릭 한 칸) |
|---|---|
| 8m | 3.1cm |
| **약 26m** | **약 10cm** |
| 150m | **58.6cm** |

엔진이 가정하는 클릭 정확도는 **±5cm**다`[구현: CORR_CLICK_SD_M=0.05, 스펙(구배·정합) §9.3]`. 셀 하나가 10cm를
넘으면(= 긴 변이 약 26m를 넘으면) **그 가정이 성립하지 않는다.** 150m 복도라면 클릭 한 칸이
58.6cm이므로, 아무리 정성껏 찍어도 대응점 오차가 반 미터 단위다.

> **권고: 한 정합이 커버하는 범위를 긴 변 26m 안쪽으로 잡는다**`[추정]`. 더 넓은 현장은 26m 이하
> 구역으로 나눠 각각 정합하거나, 애초에 측정위치를 나눠 별도로 판정한다(7.2절). 이 26m는 스펙이
> 정한 값이 아니라 **위 표에서 ±5cm 가정이 깨지는 지점을 역산한 것**이다.

### 9.5 정합 결과를 어떻게 믿을 것인가 (반드시 읽을 것)

**RMSE가 좋다는 것은 "수직으로 잘 맞았다"는 뜻일 뿐이다.**

**(1) RMSE는 수직 방향만 보증한다.** 시스템이 쓰는 point-to-plane RMSE는 어긋남의 **법선 방향
성분만** 세므로, 평탄한 바닥에서는 수평으로 아무리 어긋나도 값이 오르지 않는다`[실측]`.

| 바닥 | 수평으로 어긋난 양 | 정합 잔차 RMSE | 시스템 판정 |
|---|---|---|---|
| 범프(요철) 있는 바닥 | 200mm | 2.865mm | 탈락 |
| **완전 평면** | **1000mm** | 1.004mm | **통과** |
| **완전 평면** | **3000mm** | 1.006mm | **통과** |

**완전 평면에서는 3m를 통째로 틀리게 찍어도 RMSE 1.006mm로 "성공"이 나온다.** 결과 화면도 같은
사실을 밝힌다 - "이 수치는 수직 방향 일치만 보증합니다. … 이 숫자만 보고 승인하지 마세요."
`[구현: registration-workbench.tsx]`

**(2) "수평 검증 가능성: 낮음"은 이상이 아니라 정상이다.** 결과 화면에는 **"수평 검증 가능성: 낮음"**
또는 **"수평 검증 가능성: 있음"** 이 뜬다`[구현: registration-workbench.tsx, 임계 1.1]`. 이 값(수평 감도)은
**바닥이 평탄할수록 낮아진다**`[실측]`.

| 바닥 평탄도 | 수평 감도 |
|---|---|
| ±12mm (이 용역 기준으로는 불합격 바닥) | 1.710 |
| ±6mm | 1.218 |
| **±3.5mm** | **1.084** |
| ±2.5mm | 1.038 |

임계가 1.1이고 교차점이 **약 ±4.5mm**이므로, **이 용역이 목표로 하는 좋은 바닥일수록 "낮음"이
나온다.** 즉 이 표시는 스캔이 잘못됐다는 신호가 아니라 **"이 바닥에서는 데이터만으로 수평 위치를
판별할 정보가 원래 없다"** 는 고지다. **바닥에 구배가 있다고 구제되지도 않는다** - 최악 방향으로
집계하므로 0~20% 램프가 전부 1.002로 나온다`[실측]`.

**(3) 겹쳐보기도 만능이 아니다.** 겹쳐보기는 RMSE가 못 보는 수평 방향을 눈으로 보는 수단이지만,
분해능에 한계가 있다. 겹친 영역 무늬의 상관값`[실측]`:

| 바닥 | 정합이 맞은 경우 | 3m 오정합 | 30cm 오정합 |
|---|---|---|---|
| 특징(요철)이 있는 바닥 | +0.996 | -0.176 | - |
| **현실적 ±5mm 평탄 바닥** | **+0.896** | +0.129 | **+0.840** |
| 순수 백색잡음뿐인 완전 평면 | +0.014 | +0.043 | - |

**미터급 어긋남은 확실히 보인다**(0.896 대 0.129). 그러나 **30cm급은 정합이 맞은 경우와 거의
구별되지 않고**(0.840 대 0.896), **특징이 전혀 없는 바닥에서는 정합이 맞아도 신호 자체가 없다**(0.014).

**(4) 결론.** 세 가지 확인 수단이 모두 수평 방향에서 약하다. 따라서 **수평 방향의 실질적 보장은
9.3절이 말하는 대로 대응점을 넓게 분산해 정확히 찍는 것뿐이다.** 정합한 결과를 시공 판단에 쓸 때는 이
한계를 함께 보고한다.

### 9.6 구배가 있는 바닥의 정합은 3%까지다

클릭 오차 ±5cm 조건에서 바닥 구배를 바꿔가며 잰 z 오차다`[실측]`.

| 바닥 구배 | 정합 후 z 오차 |
|---|---|
| 0% | 0.008mm |
| 2% | 0.611mm |
| **3%** | **0.883mm** (아래 1mm 기준의 한계) |
| 5% | 1.477mm |
| 15.0% | 4.841mm |
| **15.5%** | **5.056mm** (바닥 측정 불확도 ±5mm 초과) |
| 20% | 7.037mm |

**이 프로젝트가 정합에 요구하는 z 정확도 기준은 1mm이고, 그 기준이 성립하는 것은 구배 3%까지다**
`[구현: engine/tests/test_registration.py의 회귀 시험이 z 오차 1mm 이하를 단언한다]`. 바닥 측정
불확도 ±5mm 안에 드는 범위는 15%까지다. 배수 구배(보통 1~2%)는 여유 있게 범위 안이지만,
**주차장 램프급 급구배 현장은 검증 범위 밖이다.**

> **주의 - 이 1mm는 시험 기준이지 실행 시 게이트가 아니다.** 정합을 실행할 때 엔진이 실제로 거르는
> 것은 최종 RMSE 2mm 초과·수렴 실패·중첩 부족이고`[구현: MAX_RMSE_M=0.002]`, **z 오차는 따로 검사하지
> 않는다.** 실제로 위 표의 구간 전체에서 엔진은 수렴 성공을 보고한다`[실측]`. 즉 **급구배 때문에
> 정합이 나빠져도 시스템이 스스로 알려주지 않는다.** 급구배 바닥은 정합으로 합치지 말고 구역을
> 나눠 별도 측정위치로 판정한다`[추정]`.

### 9.7 병합 스캔이 만들어진 뒤

- 병합 스캔의 **데이터 계보는 "정합 병합"** 으로 표시된다`[구현: dashboard/lib/domain/labels.ts]`.
  업로드 화면에서 고르는 값이 아니라 시스템이 붙이는 값이다
- 스캔 상세 화면에 **"두 스캔을 정합해 만든 병합 스캔입니다."** 안내와 **"정합 결과·겹쳐보기 확인"**
  링크가 붙는다`[구현: dashboard/app/scans/[id]/page.tsx]`
- **겹쳐보기 확인 체크는 권고이지 시스템 게이트가 아니다.** 화면이 직접 그렇게 밝힌다 - "병합
  스캔은 정합이 성공한 시점에 이미 만들어져 있습니다… 체크하지 않아도 병합 스캔은 측정위치
  목록과 스캔 상세에 이미 나타나 있고, 스캔 상세의 "평활도 분석" 버튼을 누르면 이 겹쳐보기를
  한 번도 보지 않은 채로 분석이 시작됩니다."`[구현: registration-workbench.tsx]`.
  **즉 확인을 건너뛰어도 아무도 막지 않는다. 담당자가 스스로 지켜야 한다**
- 병합 점군은 이미 미터로 환산돼 있어 **단위 확인 절차(8장)를 다시 거치지 않는다**
  `[구현: dashboard/app/scans/[id]/page.tsx]`
- 쓰지 않기로 한 정합은 **"대응점 다시 찍기"** 로 병합 스캔까지 정리한다(9.2절). 그대로 두면
  아무도 쓰지 않을 스캔이 목록에 남는다

## 10. 구배(경사) 측정을 함께 할 때

이 가이드라인은 평활도(평탄도) 기준으로 쓰였다. 같은 스캔으로 **구배(물매) 판정**도 하는 경우
아래 세 가지가 추가로 적용된다.

### 10.1 판정 단위가 2m x 2m 격자다

평활도는 1m x 1m 판정 셀을 쓰지만(3.4절), **구배는 2m x 2m 격자 단위로 판정한다**
`[구현: engine/flatness/core/slope.py compute_slope_cells cell_m=2.0, 스펙(구배·정합) §4.2]`. 서브셀(5cm)은
평활도와 공유하므로 2m 셀 하나가 40 x 40 서브셀이다.

현장에서 바뀌는 것: **격자 가장자리에서 폭이나 높이가 1m(= 2m의 절반)에 못 미치는 조각 셀은
판정에서 빠진다**`[구현: 같은 파일 - cell_m/2 조건]`. 즉 **판정하려는 구역은 2m 단위로 여유 있게
덮어 스캔해야** 자투리가 통째로 빠지지 않는다`[추정]`.

### 10.2 배수구는 화면에서 클릭해 지정한다

배수 방향(역구배) 판정은 **배수구 위치를 알아야** 가능하다. 이 값은 스캔 파일에 들어 있지 않고,
**구배 분석 결과 화면의 히트맵을 클릭해** 지정한다`[구현: dashboard/components/analysis/slope-result.tsx]`.

- 안내 문구: **"배수구 위치를 클릭하세요. 클릭하면 그 지점을 기준으로 재판정 작업이 시작되고,
  완료되면 화면이 자동으로 갱신됩니다."**`[구현: slope-result.tsx]`
- 배수구를 지정하지 않으면 **"배수구가 지정되지 않아 방향(역구배)은 판정하지 않았습니다."** 가 뜬다
  `[구현: dashboard/components/analysis/slope-verdict-panel.tsx]`
- 클릭 대상 히트맵은 **판정된 구배 셀의 범위만 덮는다**`[구현: dashboard/components/analysis/slope-heatmap-view.tsx]`.
  따라서 **배수구가 스캔 범위 안에 들어와 있어야 클릭할 수 있다.** 배수구 주변을 스캔에서
  빠뜨리지 않는다`[추정]`
- 방향을 판정하지 않는 기준을 적용한 분석에서는 클릭이 비활성화되고 그 이유가 표시된다`[구현: slope-result.tsx]`

### 10.3 급구배 현장은 정합 검증 범위 밖이다

구배가 있는 바닥을 정합으로 합치려 한다면 **9.6절을 먼저 읽는다.** 정합의 z 게이트는 구배 3%까지
성립하며, 주차장 램프급 급구배 현장은 검증되지 않았다`[실측]`.

## 11. 스캔 품질 자가 점검 (경고 코드별 조치)

분석이 끝나면 결과 화면과 보고서에 경고 배지가 뜬다. 경고 코드의 정의는
[`contracts/stats-schema.md`](contracts/stats-schema.md) §5가 정본이며, 아래는 **현장 담당자가
할 조치**를 덧붙인 것이다.

### 11.1 재스캔이 필요한 경고

| 경고 코드 | 화면 표시 의미 | 원인 | 재스캔 방법 |
|---|---|---|---|
| `ghost_layer_rescan` | 이중 표면(유령층) 감지, 해당 지역 판정 불가 | 같은 지점을 두 번 지나며 위치 추적이 어긋나 바닥이 두 겹으로 기록됨(높이 간극 8mm 초과)`[구현]` | **재스캔 필수.** 이동 속도를 낮추고, 왕복 대신 한 방향 지그재그로 훑는다. 폐루프로 종료한다 |
| `ghost_zone_excluded` | 구역 전체가 통째로 제외됨 | 위와 같은 현상이 **한 구역의 20%를 넘음**`[구현: ghost_frac=0.2]` | **재스캔 필수.** 위와 동일하되, 해당 구역을 별도로 나눠 짧게 스캔한다 |
| `low_coverage` **(바닥 분석 전용)** | 바닥 인식률 70% 미만 | 바닥이 가려졌거나(자재·가구), 스캔 범위가 부족하거나, 점이 성겨 서브셀이 버려짐 | 장애물을 치우고(2.2절), 빠진 영역을 채워 다시 스캔한다. 점 간격 2cm 이하를 확보한다(3.4절). **벽면 분석에서는 이 경고가 발생하지 않는다**`[구현: analyze_floor에서만 판정]` |
| `wall_{n}_skipped` | n번 벽이 판정에서 제외됨 | 그 벽의 유효 점이 부족하거나(서브셀 10개 미만) 투영·피팅에 실패`[구현]` | 해당 벽을 **정면에서 위아래로** 다시 훑는다. 높이 0.8m·길이 1.0m 조건을 확인한다(5장) |

### 11.2 재스캔이 아니라 판단·설정 문제인 경고

| 경고 코드 | 의미 | 조치 |
|---|---|---|
| `furniture_excluded` | 가구 상판으로 추정되는 면이 제외됨 | **의도된 제외라면 무시한다.** 그 면을 판정해야 한다면 별도 측정위치로 스캔한다(2.2절) |
| `reduced_span` | 일부 셀이 축소 스팬으로 판정됨 | 공간이 3m가 안 되면 정상이다. 3m를 확보할 수 있는데도 떴다면 스캔 범위가 잘린 것이니 넓혀서 재스캔한다 |
| `uncertainty_swallows_repair` | 측정 불확도가 보수 구간을 잠식함(`pass + U >= rework`) | **스캔 문제가 아니라 기준/불확도 조합의 문제다.** 담당자에게 알리고 적용 기준을 재검토한다([`criteria-sources.md`](criteria-sources.md) 참고) |
| `uncertainty_swallows_pass` | 측정 불확도가 허용치보다 커서(`b1 = pass - U <= 0`) **적합 판정이 원리적으로 나올 수 없음** | **스캔 문제가 아니다. 아무리 잘 스캔해도 적합이 나오지 않는다.** 탑재된 벽면 평활도 기준 4종 중 3종이 기본 U=8mm에서 여기 해당한다(`wall-kcs-tilt-exposed`·`wall-plaster-base` -2mm, `wall-plaster-surface` -5mm). 담당자에게 알리고 적용 기준 또는 U를 재검토한다([`criteria-sources.md`](criteria-sources.md) 6.2절) |
| `plumbness_relative_to_z` | 수직도가 z축 기준 상대값 | 벽면 분석에 **항상** 붙는 고지다. 수직도 절대값이 필요하면 별도 레벨 측량이 필요하다 |

### 11.3 스캔과 무관한 경고 (시스템 문제)

`heatmap_render_failed`, `preview3d_render_failed`, `deviation_render_failed`는 그림 생성이
디스크·폰트 등 인프라 사유로 실패했다는 뜻이다. **판정 수치는 영향받지 않는다**`[스펙 계약 §5]`.
재스캔하지 말고 시스템 담당자에게 알린다.

### 11.4 경고가 없어도 확인할 것

경고가 하나도 없어도 아래는 눈으로 확인한다.

1. **바닥 인식률(coverage)** 이 90% 이상인가. 70~90%는 경고가 뜨지 않지만 상당 부분이 빠진 것이다
2. **판정 불가(na) 셀**이 많지 않은가. 많다면 점 밀도나 가림 문제다
3. **전 셀이 경계**로 나오지 않았는가. 1장의 실측대로 **노이즈가 지배하고 있다는 신호일 수
   있다.** 결함이 없는 바닥인데 전 셀 경계라면 스캔 품질을 의심하고 재스캔한다`[실측]`
4. **정밀 편차맵**을 본다. 결함이 있으면 특정 위치에 모양을 갖고 뭉쳐 보인다. 화면 전체가
   자잘하게 얼룩덜룩하면 노이즈다`[스펙: 편차맵 설계]`

## 12. 현장 체크리스트

스캔 직전에 훑는 용도다.

**준비**
- [ ] 조명 켜짐, 스캔 중 소등되지 않음
- [ ] 판정 대상 바닥의 자재·공구 정리 완료
- [ ] 젖은 바닥 없음, 거울·유리면 확인
- [ ] 스캔 중 통행 통제
- [ ] 스캔 범위 결정(넓으면 구역 분할)

**스캔**
- [ ] 시작점 기억(폐루프 종료)
- [ ] 기기와 대상면 거리 0.3~1.5m 유지
- [ ] 천천히 이동, 급회전 없음
- [ ] 바닥-벽 접합부 포함해 훑음
- [ ] 벽면은 정면에서 위아래로 훑음
- [ ] 시작점으로 복귀해 종료

**저장·업로드**
- [ ] 원시 점군으로 내보내기(융합 메시 아님). 불가피하면 계보에 직접 표기(자동 감지 안 됨)
- [ ] 지원 확장자 확인(ply/las/laz/pts/xyz/txt/csv), 50MB 이하(초과 시 7.2절 - 구역을 나눠
      별도 측정위치로 올린다)
- [ ] 소수점이 마침표인지 확인(쉼표 로케일은 조용히 오파싱됨)
- [ ] 측정위치·표면 유형·측정일자·담당자·장비 입력
- [ ] 적용 판정 기준 확인
- [ ] **스캔 앱의 내보내기 설정에서 좌표 단위를 확인한 뒤 단위 확인 화면에서 선택**
      (단위 확인 화면의 **높이 뷰 축 눈금**을 실제 공간 크기와 대조한다. 8m 방인데 눈금이
      8000까지 가면 mm다. 후보·신뢰도는 여전히 표시되지 않고, 그림이 없는 스캔도 있다. 8장 참고)

**나눠 찍어 정합할 때(9장)**
- [ ] 두 스캔 모두 단위 확정까지 끝나 "분석 준비됨"인지 확인(바닥 스캔만 가능)
- [ ] 대응점 8쌍 이상, **정합 영역 전체에 넓게 분산**해서 찍음(한곳에 몰리면 거부됨, 9.3절)
- [ ] 한 정합이 덮는 범위의 긴 변이 26m 이하인지 확인(넘으면 클릭 한 칸이 10cm를 넘는다, 9.4절)
- [ ] **RMSE만 보고 승인하지 않음.** 겹쳐보기로 수평 방향을 눈으로 확인(9.5절)
- [ ] "수평 검증 가능성: 낮음"이 떠도 이상이 아님을 이해하고 있음(9.5절)
- [ ] 바닥 구배가 3%를 넘으면 정합으로 합치지 않음(9.6절)

**구배도 판정할 때(10장)**
- [ ] 판정 구역을 2m 격자로 여유 있게 덮어 스캔(자투리 조각 셀은 판정에서 빠짐, 10.1절)
- [ ] **배수구가 스캔 범위 안에 들어오게** 찍음(결과 화면에서 클릭해 지정한다, 10.2절)

**결과 확인**
- [ ] 경고 배지 확인(11장 표에 따라 조치)
- [ ] 바닥 인식률 확인
- [ ] 전 셀 경계 여부 확인(노이즈 지배 신호)
- [ ] 정밀 편차맵에서 결함이 모양을 갖는지 확인

## 13. 이 가이드라인의 한계

정직하게 밝힌다.

- **실제 현장에서 실물 직선자와 대조한 검증이 아직 수행되지 않았다**`[스펙 §10.4가 요구했으나 미수행]`.
  따라서 "이렇게 스캔하면 정확도가 얼마나 좋아지는가"에 대한 정량적 근거가 없다
- 1장의 노이즈 실측은 **합성 데이터**에 가우시안 노이즈를 주입한 결과다. 실제 LiDAR 노이즈는
  가우시안이 아니고 공간적으로 상관되어 있을 수 있어, 실제 배율은 다를 수 있다`[추정]`
- 3장의 이동 경로·속도 권고는 대부분 `[추정]`이며 이 프로젝트가 반복 스캔으로 검증하지 않았다
- 측정 불확도 U(바닥 5mm, 벽 8mm)는 **잠정치**다`[스펙 §4.2]`. 반복 스캔 재현성 시험으로
  갱신하기로 되어 있으나 아직 수행되지 않았다
- 앱별 특성(어떤 iPhone 앱이 더 정확한가, 중력 기준을 보장하는가)에 대한 검증 목록이 없다
- **정합(9장)의 수평 방향 정확도를 시스템이 검증하지 못한다.** RMSE·수평 감도·겹쳐보기 세
  수단이 모두 평탄한 바닥에서 약하다는 것을 실측으로 확인했다(9.5절). 이 한계는 해소된 것이
  아니라 **문서로 고지된 상태**이며, 정합 결과를 쓸 때는 함께 보고해야 한다
- 정합의 실측값(9.3~9.6절)은 전부 **합성 픽스처에서 잰 값이다**`[실측]`. 실제 현장 스캔 두 개를
  정합해 실물과 대조한 검증은 수행되지 않았다
- 9.4절의 26m 권고와 9.3절의 8쌍 권고는 **구현 상수에서 역산한 실무 선이며**`[추정]`, 스펙이
  정한 값도 현장에서 검증한 값도 아니다
