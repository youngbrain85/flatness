## 1. 과업 개요

### 1.1 목적

모바일 LiDAR(iPhone/iPad)로 스캔한 현장 바닥면·벽면 포인트클라우드를 업로드하면, 국내 시방서
기준으로 평활도를 분석·판정하고, 결과를 온라인 DB에 축적하며, 수직·수평면 통합 PDF 보고서를
자동 생성하는 시스템을 개발한다.

기존 방식(Colab 노트북 수동 실행)의 한계를 해소하는 것이 재설계의 동기였다.

| 기존 방식의 문제 | 본 시스템의 해소 방식 |
|---|---|
| Colab 세션 종속. 결과가 세션과 함께 소멸, 이력·공유·비교 불가 | 온라인 DB에 영속 저장, 현장·측정위치 체계로 조회 |
| 단일 전역 RANSAC 평면. 다중 방·단차·설계 구배에서 오판, 벽면 미지원 | 구역 분할 후 구역별 평면 재피팅, 벽면 파이프라인 신설 |
| 판정 기준 근거 부재(임의 임계값 9mm 슬라이더) | 국내 시방서 기준 11종 탑재, 적용 기준을 분석 결과에 박제 |
| 포인트별 Python 루프, 무작위 샘플링 시각화로 결함 누락 가능 | 서브셀 충분통계량 누적, 전 라인 스윕으로 결함 누락 방지 |
| 메타데이터·연계·보고서 없음, 실제 LiDAR 포맷 미지원 | 메타데이터·사진 연계·자동 PDF 보고서, 7종 포맷 지원 |

### 1.2 범위

> **이 절은 세부과업 1의 범위다.** 세부과업 4(구배 자동 측정·분석)의 범위는 9.1.2절에 따로
> 있다. 아래 "제외" 항목에서 세부과업 4가 빠진 것은 **9장이 그 과업을 별도로 보고하기
> 때문**이며, 세부과업 2·3은 여전히 미착수다.

**포함**
- 바닥면(수평)·벽면(수직) 평활도 분석 및 4등급 판정
- 온라인 대시보드 (업로드, 현장·측정위치 관리, 결과 조회, 사진 연계)
- 온라인 DB (Supabase Postgres) 및 파일 저장소
- 수직·수평 통합 PDF 보고서 자동 생성 (자동 종합의견 + 사용자 수정)
- 판정 기준 관리 (전역 기본값 + 현장별 재정의)
- 기존 분석 프로그램 결과 데이터 임포트 (Colab 노트북 CSV + 범용 JSON `flatness-import-v1`)

**제외** (설계 정본 §2.2에서 명시적으로 제외를 결정한 항목)
- 과업지시서 세부과업 2·3 (마감재 DB, BIM-API 연계, 로봇 작업 모니터링·시뮬레이션). 단,
  데이터 포맷·산출물 형식은 향후 연계가 가능하도록 유지 (7장 참고)
- 과업지시서 **세부과업 4**(구배 알고리즘)는 세부과업 1 설계 시점에는 제외였으나, 세부과업 1
  완료 후 **별도 과업으로 착수해 구현했다. 그 결과는 9장이 보고한다**
- E57 파서 (현재 사용 장비가 내보내지 않는 TLS 중심 포맷. 파서 인터페이스만 추상화)
- 모바일 전용 앱, 실시간 스캔 스트리밍, 다중 조직 권한 체계, 계단 분석
- 벽면 단차(step) 지표. 지표는 flatness/plumbness 2종으로 한정

셀을 뜻하며 경계는 포함하지 않는다(템플릿에 각주로 명시됨). **셀 단위 상세**(셀 인덱스·중심
좌표·편차값·사용 스팬·등급·최대 결함 지점 좌표)는 보고서 결과표가 아니라 산출물
`results.csv`·`cells.json`과 대시보드 결과 화면의 셀 상세 패널로 제공한다
([`contracts/stats-schema.md`](contracts/stats-schema.md) §6).

**② 가. "돌출·함몰 편차 산정"에 대한 설명**: 본 시스템의 판정값은 실물 3m 직선자를 그대로
시뮬레이션한 값이라 **상부 볼록 포락선 아래 최대 틈새**다. 이 값은 정의상 0 이상인 단일
스칼라이며, 실물 직선자로 재는 값과 마찬가지로 돌출량과 함몰량이 하나의 수치로 합쳐진다.
돌출·함몰의 **구분과 분포**는 부호를 보존한 **정밀 편차맵**(10cm 격자, 0mm 중심 대칭 발산
색상)이 담당하며, 벽면은 `+w` = 실내 방향 돌출 / `-w` = 함몰, 바닥은 `+` = 융기 / `-` = 침하가
코드 상수·범례·테스트로 고정되어 있다. 즉 **요구 항목은 "판정값 + 부호 있는 편차맵" 두 산출물의
조합으로 이행**되며, 판정값 하나만 놓고 보면 부호가 없는 것이 설계 의도다.

**② 다. 3구간과 4등급의 대응**:

| 과업지시서 구간 | 본 시스템 등급 | 판정식 |
|---|---|---|
| 적합 구간 | **적합** | 지표 <= `b1` |
| (해당 구간 없음 - 본 시스템이 신설) | **경계** (현장 재확인 필요) | `b1` < 지표 <= `b2` |
| 보수 구간 | **보수** | `b2` < 지표 <= `re` |
| 재시공 검토 구간 | **재시공** | 지표 > `re` |

"경계"는 측정 불확도 U 때문에 합격/불합격을 단정할 수 없는 구간을 정직하게 분리한 것으로,
**시방서에도 과업지시서에도 없는 본 시스템의 해석**이다(4.1절,
[`criteria-sources.md`](criteria-sources.md) 5장). 3구간 요구 자체는 4등급으로 세분해 충족한다.

### 2.5 이행 현황 요약

아래 숫자는 **과업지시서 원문 항목 수가 아니라 위 2.1~2.4 표의 세분 행 수**다. 원문 한 항목을
산출물 단위로 여러 행으로 나눠 적었기 때문이며, `(추가 지원)`으로 표기한 요구 항목 외 행은
집계에서 제외했다. 괄호 안이 과업지시서 원문의 항목 수다.

| 구분 | 원문 항목 수 | 세분 행 (완료) | 부분 | 미이행 |
|---|---|---|---|---|
| 가. 분석 결과 연계 성과물 | 3 | 9 | 0 | 0 |
| 나. 자동 보고서 생성 성과물 | 3 | 6 | 0 | 0 |
| 다. 보고서 관리 성과물 | 3 | 4 | 0 | 0 |
| 기술 요구사항 | - | 18 | 0 | 0 |
| 라. 용역 결과 보고서 | 1 | 본 문서 | - | - |

**요구 항목 기준 미이행 0건, 부분 이행 0건**이다. 직전 판까지 부분 이행으로 남아 있던 범용
JSON 임포트 파서는 구현이 완료되어(2.1·2.4절) 부분 이행 항목이 없다.

> 다만 "미이행 0건"은 **과업지시서 요구 항목** 기준이다. 설계 정본이 계획했으나 구현되지 않은
> 항목은 6.5절에 따로 열거했고, 검증 측면의 미수행 항목은 5.6절에 있다. 특히 **실물 직선자
> 실측 대조와 시방서 원문 대조는 수행되지 않았다.**
>
> **또한 이 "미이행 0건"은 세부과업 1에만 해당한다.** 세부과업 4의 이행 현황은 9.2절에 따로
> 있고, 그쪽에는 **부분 이행 항목이 있다.**

## 3. 시스템 구성

### 3.1 4계층 구조

```
  [1] 분석 엔진 (Python)          engine/flatness/
       파서 -> 서브셀 비닝 -> 구역 분할 -> 직선자 시뮬레이션 -> 판정 -> 산출물
                      |
  [2] 온라인 DB (Supabase)        supabase/migrations/
       메타데이터 · 판정 결과 · 인증 · Realtime · 잡 큐 · 사진 Storage
                      |
  [3] 분석 워커 (Python)          worker/flatworker/
       잡 큐 폴링 -> precheck / analyze / import / report 처리
                      |
  [4] 웹 대시보드 (Next.js)       dashboard/
       업로드 · 현장 관리 · 단위 확인 · 결과 조회 · 보고서 생성·발행
```

계층 간 결합은 **DB의 잡 큐와 데이터 계약 문서**로만 이루어진다. 워커와 대시보드는 서로를
직접 호출하지 않으며, 산출물의 형식은 `docs/contracts/stats-schema.md`가 정본이다.

### 3.2 기술 스택

| 계층 | 기술 | 주요 의존성 |
|---|---|---|
| 분석 엔진 | Python 3.11 | numpy >= 1.26, scipy >= 1.11, laspy[lazrs] >= 2.5, matplotlib >= 3.8 |
| DB / 인증 | Supabase (PostgreSQL) | Postgres + Auth + Realtime + Storage, RLS 전 테이블 활성화 |
| 분석 워커 | Python 3.11 | httpx, python-dotenv, numpy, matplotlib, jinja2, playwright |
| 웹 대시보드 | Next.js 16.2.12 (App Router, TypeScript) | React 19.2.4, @supabase/ssr, @supabase/supabase-js |

**"Python 기반" 요구에 대한 설명**: 과업지시서가 요구한 Python 기반은 **분석·판정·보고서 생성
전 계층에서 충족**된다. 웹 대시보드만 브라우저 UI 계층이라 TypeScript로 구현했으며, 이 계층은
분석 로직을 전혀 포함하지 않고 DB 조회·표시·파일 업로드만 담당한다. 대시보드 없이 CLI만으로도
분석·판정·산출물 생성이 완결된다(`flatness analyze <파일> --out <디렉터리> --units m`.
`engine/pyproject.toml`의 `[project.scripts]`가 등록하는 콘솔 스크립트다. 임포트는
`flatness import-colab` / `flatness import-json`).

**주요 라이브러리 채택 현황에 대한 설명**: 과업지시서 세부과업 4(11쪽 "나. 알고리즘 사양")는
주요 라이브러리로 Open3D·PCL(Point Cloud Library)·NumPy·scikit-learn(RANSAC 평면 피팅)을
명시한다. 세부과업 1 자체의 기술 요구사항(3쪽)에는 별도 라이브러리 지정이 없으나, 세부과업 4의
엔진이 세부과업 1과 같은 Python 패키지(`engine/`)를 공유하므로 이 채택 여부를 여기서 함께
밝힌다. 본 시스템은 이 중 **NumPy만 채택**했고 **Open3D·PCL·scikit-learn은 쓰지 않는다.**

- **평면 피팅(RANSAC)**: scikit-learn이 아니라 NumPy로 직접 구현했다(`engine/flatness/core/plane.py`).
  세부과업 1의 구역별 평면 재피팅(4.2절)이 이미 이 구현을 쓰고 있었고, 잘 동작하는 코드를
  라이브러리로 교체하면 회귀 위험만 생기고 얻는 것이 없다고 판단했다
- **Open3D**: 채택하지 않았다. Linux wheel이 400MB대이고 libGL·libgomp 등 무거운 시스템
  의존성을 끌고 들어와, Playwright Chromium이 이미 들어간 워커 컨테이너의 이미지 크기와
  빌드 시간에 부담이 크다
- **PCL**: C++ 라이브러리라 Python 스택에 넣지 않았다

현재 엔진 의존성은 **numpy·scipy·laspy·matplotlib 4개**뿐이다(`engine/pyproject.toml`). 워커는
여기에 httpx·python-dotenv·jinja2·playwright를 더한다(`worker/pyproject.toml`). 루트
`Dockerfile`도 Open3D·PCL 관련 시스템 패키지(libGL 등)를 설치하지 않는다.

**이는 미이행이 아니라 의도적 이탈이며 발주처가 승인한 사항이다.** 사용자가 "과업지시서에 있는
라이브러리들은 무시해도 괜찮다. 무슨 소프트웨어를 쓰고 어떤 언어로 할지는 상관 없다. 뭐로 하든
결과만 나오면 되는거야"라고 명시적으로 승인했고(2026-08-02,
[`superpowers/specs/2026-08-02-slope-analysis-design.md`](superpowers/specs/2026-08-02-slope-analysis-design.md)
§1.3), 이후 **개별 승인이 아니라 상시 방침으로 확정했다**(2026-08-09). 세부과업 1이 실제로
요구한 처리 환경(Python)과 결과 파일 형식(CSV·JSON·PNG·PDF, 2.4절)은 전부 그대로 준수한다.

**이 절의 이탈은 단발 예외가 아니다.** 방침의 전문과 적용 사례 전수(6건), 그리고 **무엇이
구속력 있는 요구이고 무엇이 참고인지의 구분**은 9.2.1절에 모아 두었다. 요약하면 **언어·
라이브러리·소프트웨어·알고리즘 구현 방식은 참고**이고, **산출물 형식·정밀도 사양·분석 단위·
산출 항목은 구속력 있는 요구**다.

### 3.3 데이터 흐름

```
[iPhone/iPad LiDAR 앱]
   |  PLY / LAS / LAZ / XYZ / TXT / CSV / PTS
   v
① 대시보드 업로드
   현장·측정위치 지정, 메타데이터 입력(표면 유형·측정일자·담당자·데이터 계보·적용 기준)
   -> Supabase Storage raw-scans 버킷 저장 -> scans 행 생성
   v
② precheck 잡 (워커)
   파싱·단위 추정 -> 사용자가 단위 확정 (자동 확정하지 않음)
   v
③ analyze 잡 (워커) - 단위 확정 시 자동 등록
   잡 큐를 FOR UPDATE SKIP LOCKED로 클레임 -> 엔진 호출
   v
④ 결과 저장
   판정 수치 -> analyses (DB) / 산출물 PNG·CSV·JSON -> artifacts 버킷/{analysis_id}/
   v
⑤ 대시보드 결과 화면
   Supabase Realtime으로 진행 상태 반영 -> 히트맵·판정 패널·결과표·편차맵 표시
   v
⑥ report 잡 (워커)
   같은 측정위치 분석 복수 선택 -> 자산 복사 + snapshot 박제 -> Jinja2 HTML
   -> Playwright Chromium -> report.pdf -> 발행(finalized, 이후 수정 차단)

(별도 경로) 기존 결과 임포트: Colab CSV 또는 범용 JSON(`flatness-import-v1`) 업로드
   -> import 잡(확장자로 파서 분기) -> analyses(external) 등록
(별도 경로) 재분석: 이미 분석이 끝난 스캔을 같은 표면·기준으로 다시 실행
   -> 원본이 임포트 결과면 import 잡, 스캔 원본이면 analyze 잡
```

### 3.4 잡 큐 설계

동시성·장애 복구를 DB와 워커 양쪽에서 처리한다.

- **클레임 (DB 보장)**: `FOR UPDATE SKIP LOCKED` 단일 트랜잭션 (`fn_job_claim`) - 워커가 여러
  개여도 같은 잡이 이중 실행되지 않는다
- **중복 방지 (DB 보장)**: `COALESCE(payload->>'analysis_id', payload->>'scan_id', payload->>'report_id')`
  기준 부분 유니크 인덱스 (status가 queued/processing인 행만)
- **재시도**: 최대 3회, `run_after` 백오프
- **고착 회수**: `fn_reap_stuck_jobs`가 30분 초과 processing 잡을 queued로 되돌리고
  analyses·scans·reports의 상태를 동반 복구
- **동시 실행 없음 (워커 구조에서 나옴, DB 보장 아님)**: `fn_job_claim`은 **잡 타입과 무관하게**
  `created_at` 순으로 1건만 클레임한다. 분석 잡과 보고서 잡이 동시에 돌지 않는 것은 워커의
  `run_loop`가 단일 프로세스로 한 번에 1건만 처리하기 때문이며, **워커를 2개 이상 띄우면 이
  성질은 보장되지 않는다**(데모 구성은 단일 워커). 설계 정본 §3.1의 "잡 type별 직렬 실행"은
  이 단일 워커 전제에서 성립하는 서술이다
- **전송 오류 복원력 (본 갱신에서 반영)**: Supabase가 유휴 keep-alive 연결을 끊은 뒤 워커가 그
  연결을 재사용하면 `httpx.RemoteProtocolError`가 발생해 **워커 프로세스가 죽던 문제**가
  있었다(시연 중 실측). 두 층으로 해소했다. ① 폴링 루프의 `claim_job` 전송 오류는 지수
  백오프(최대 60초)로 재시도하며 복구 시 간격을 원복한다 ② 잡 큐 4종
  (`claim_job`/`complete_job`/`fail_job`/`reap_stuck_jobs`)에 짧은 재시도를 공통 적용해,
  수 분 걸리는 분석 도중 연결이 끊겨 `complete_job`이 실패하면서 **성공한 분석이 실패로
  기록되던** 경로를 좁혔다. `DBError`(HTTP 4xx/5xx, 인증 실패 등)는 재시도해도 무의미한 영구
  오류이므로 한국어 사유를 남기고 그대로 종료한다`[구현: worker/flatworker/runner.py, db.py]`

### 3.5 운영 비용

클라우드 배포 구성 기준 월 **$5**다. 다만 파일 저장을 로컬 디스크에서 Supabase Storage로 옮기며
**업로드 상한이 1 GiB에서 50MB로 낮아졌다**`[구현: dashboard/lib/upload/validate.ts
MAX_UPLOAD_BYTES]`. 로컬 디스크에 저장하던 시절에는 대용량 파일이 Supabase를 거치지 않아 Free
티어 제한(파일당 50MB·총 1GB)에 걸리지 않았지만, 지금은 업로드 자체가 이 제한을 직접 통과해야
한다 - **이번 전환은 능력 유지가 아니라 능력 축소다.** Supabase·Vercel은 무료 티어로 충분하고,
워커만 Chromium을 띄운 채 상시 대기해야 하는 컨테이너 프로세스라 Railway 유료 플랜(Hobby)이
필요하다.

> **이 상한은 5.3절의 성능 실측과 충돌한다.** 5.3절이 성능 근거로 쓴 3천만 점 PLY는 같은 절
> 말미의 점당 약 12바이트 계산을 그대로 적용하면 약 360MB로, 현재 업로드 상한(50MB)의 7배가
> 넘는다. 즉 본 보고서가 성능 검증에 사용한 파일을 이 시스템은 업로드 단계에서부터 받지 못한다.
> 해당 파일은 개발 환경에서 엔진을 직접 호출해 생성·측정한 것이며 대시보드 업로드 경로를 거치지
> 않았다.
>
> **다만 그 파일은 권장 밀도의 스캔이 아니다.** 성능 시험 조건인 점 간격 약 4.5mm는
> `scan-guideline.md` 1.1절이 실측으로 검증한 조건(2cm)보다 면적당 점 수 기준 약 20배 촘촘하다.
> 같은 30m x 20m(600 m²) 바닥을 점 간격 2cm로 스캔하면 약 150만 점, 위와 같은 점당 12바이트
> 기준으로 **약 18MB**이고, 판정 가능 최소 밀도인 2.9cm면 약 8.6MB다. **권장 밀도를 지키는 한
> 통상적인 실내 공간은 50MB 상한 안에 들어온다.** 상한이 실제로 문제가 되는 경우는 점 간격을
> 필요 이상으로 촘촘하게 잡았거나 한 파일에 지나치게 넓은 범위를 담으려 할 때다.

| 대시보드 | Vercel Hobby (Next.js) | $0 |

## 4. 주요 기능별 구현 내용

### 4.1 판정 알고리즘의 원리

핵심은 **실물 3m 직선자 검사를 그대로 시뮬레이션하는 것**이다.

**(1) 서브셀 대표높이** - 5cm x 5cm 격자마다 점들의 **중앙값**을 대표 높이로 삼는다. 점 단위
노이즈 극값이 판정을 지배하지 않게 하는 장치다. 점이 3개 미만인 서브셀은 신뢰도 부족으로 버린다.

**(2) 직선자 포락선** - 실물 직선자는 표면의 **고점에 얹혀** 지지되므로, 기준선은 프로파일의
**상부 볼록 껍질**(monotone chain)이다. 그 아래 최대 틈새가 그 라인의 측정값이다.

> 최소제곱 평면 방식을 쓰지 않은 이유: LSQ 평면은 데이터 중앙을 관통하므로 파형 결함을 약
> 1/2로 축소해 읽는다. 실물 직선자와 다른 값이 나오므로 설계 정본 §5.1.6이 판정 사용을 금지했다.

**(3) 전 라인 스윕** - 판정 셀(1m x 1m)마다 4방향(0/45/90/135도)에 대해 **셀 블록을 지나는
모든 서브셀 라인**을 평가한다. 셀 중심 라인만 검사하면 라인에서 벗어난 결함이 감쇠 측정되어
±1mm 정확도 요구를 위반함이 구현 검증에서 확인되어 개정된 설계다. 셀 값은 환산 허용치 대비
최악 라인의 값이다.

**(4) 4등급 판정** - `s = span_used/span`, `pe = pass x s`, `re = rework x s`, `U_eff = U x s`,
`b1 = pe - U_eff`, `b2 = min(pe + U_eff, re)`로 적합/경계/보수/재시공을 나눈다.
**이 4등급 체계와 불확도 반영은 시방서에 없는 본 시스템의 해석이다**
([`criteria-sources.md`](criteria-sources.md) 5장에 상세히 기술).

### 4.2 구역 분할 (다중 방·단차·설계 구배 대응)

기존 노트북의 가장 큰 결함이 단일 전역 RANSAC 평면이었다. 결함 구역이 RANSAC 인라이어에서
빠져 **측정 자체에서 제외되는 선택 편향**이 발생한다.

본 시스템은 구역(연결요소)을 바닥의 실체로 다룬다.

1. 서브셀 높이 히스토그램으로 레벨 밴드 검출
2. 밴드별 연결요소 분석으로 방·구역 분리 (1m² 미만 파편은 배제)
3. **평면 추종 영역 성장**: 구역별 평면을 피팅한 뒤 인접 링을 평면 기준 ±5cm로 흡수. 고정
   높이 밴드만 쓰면 경사 슬래브에서 커버리지가 붕괴하는 문제(실측: 경사 1.0%에서 100%,
   1.7%에서 68.3%, 2.5%에서 45.8%)를 해소한 개정이다
4. 구역별로 평면을 재피팅해 잔차를 산출. **평면 제거 후의 국부 요철만 판정 대상**이며, 전역
   기울기는 별도 지표로 분리한다

**자동 제외 규칙**
- 주 바닥면보다 0.3m 이상 높고 면적 3m² 이하 -> `furniture`(가구 상판)로 판정 제외
- 서브셀 높이 분포의 쌍봉성(간극 8mm 초과)이 구역의 20%를 넘으면 -> `ghost`(SLAM 유령층)로
  제외하고 재스캔 권고

### 4.3 벽면 처리

바닥과 같은 체계를 벽면 좌표계로 옮긴 구조다.

1. **벽 검출**: xy 컬럼별 z 최소/최대/점수를 누적해 높이 0.8m 이상인 컬럼을 벽 후보로 삼고,
   2D 라인 RANSAC을 반복해 최대 8개의 벽 라인을 추출
2. **팬텀 벽 차단**: 바닥과 천장만 찍히고 중간 높이가 빈 컬럼은 벽으로 인정하지 않는다
   (`cnt_mid` 조건). 천장 포함 스캔에서 허상 벽이 검출되던 문제를 근본 해소한 개정이다
3. **투영**: 벽 평면 ±10cm 내 점을 (u, v, w) 좌표로 변환. 바닥·천장 접합부 각 10cm는 제외한다
   (실물 벽 검측과 동일)
4. **부호 규약**: +w = 실내 방향 돌출. 실내 판별은 밴드 밖 점 질량 비교로 결정한다
   (bbox 중심 휴리스틱은 중심 통과 벽에서 결정적으로 실패해 폐기)
5. **판정 분리**: 셀 판정 = 평면 제거 후 국부 요철 / 수직도 = 전역 기울기(`|b| x 높이`).
   바닥의 레벨 분리와 동일한 원칙이다
6. **벽별 오류 격리**: 한 벽의 투영·피팅 실패가 전체 분석을 중단시키지 않는다. 실패한 벽만
   `wall_{n}_skipped` 경고와 함께 건너뛰고 성한 벽의 결과는 보존한다

### 4.4 보고서 자동 생성

**재현성이 설계의 중심**이다. 발행된 보고서는 원본 분석이 수정·삭제되어도 동일하게 재현되어야
한다.

1. `reports` + `report_analyses` + `analyses` + `scans` + `locations` + `sites` + `photos`를 로드하고
   사전 검증(완료되지 않은 분석·다른 측정위치의 분석은 사용자가 조치할 수 있는 한국어 사유로 거부)
2. 히트맵·3D 프리뷰·편차맵·사진을 `reports/{id}/assets/`로 **복사**하고 히스토그램을 생성
3. `reports.snapshot`(`report-snapshot-v1`)에 수치·기준·**등급 라벨과 색상 팔레트까지** 박제
4. Jinja2 HTML -> Playwright Chromium -> PDF
5. 발행(finalized) 후에는 DB 트리거가 snapshot·pdf_path 수정을 차단

자동 종합의견은 규칙 템플릿이다(LLM 미사용). 판정 분포, 최대 편차 위치, 경고 코드별 해설,
최악 등급에 따른 권고, **스크리닝 한계 고지 문구**를 조합한다. 사용자가 수정할 수 있으며
수정본도 snapshot에 박제된다.

### 4.5 정밀 편차맵

판정 히트맵은 1m 셀 단위 5색 이산 표시라 **결함의 실제 모양과 크기가 보이지 않는다.** 30cm
함몰이든 90cm 완만한 처짐이든 같은 색 사각형 하나로 뭉개진다.

정밀 편차맵은 판정에 이미 사용한 5cm 잔차 배열을 **2x2 평균 풀링**해 10cm 격자로 만들고
연속 색상(0mm 중심 대칭 발산 colormap)으로 칠한다. 점군을 다시 읽지도, 평면을 다시 피팅하지도
않으므로 추가 비용이 거의 없다.

**판정 무관성이 핵심 제약이다.** 이 기능은 판정 파이프라인에 어떤 입력도 제공하지 않고 어떤
출력도 바꾸지 않는다. 편차맵 생성이 실패해도 등급 결과는 동일하다. UI와 보고서 캡션에
"판정 등급 산출에는 사용되지 않으며, 등급은 1m 판정 셀 기준"을 항상 표시한다.

### 4.6 대시보드 사용성 개선 (최종 갱신분)

기능 범위를 넓힌 것이 아니라 **기존 기능에 도달하지 못하던 경로를 메운 변경**이다.

- **업로드 진입 승격**: 상단 내비게이션에 업로드 버튼을 두어 현장 상세 화면을 거치지 않아도
  업로드를 시작할 수 있게 했다
- **빈 상태 온보딩**: 현장·측정위치가 하나도 없는 초기 상태에서 홈 화면과 업로드 화면이 다음에
  할 일(현장 생성 -> 측정위치 생성 -> 업로드)을 안내한다. 이전에는 빈 목록만 보였다
- **재분석 버튼 신설**: 엔진 개선이나 판정 기준 변경 후 기존 스캔을 다시 돌릴 방법이 없었다
  (analyses 행은 업로드 시에만 생성됐다). 스캔 상세에서 같은 표면·기준으로 새 분석을 걸 수 있다.
  **임포트 결과 스캔은 `analyze`가 아니라 `import` 잡으로 분기한다** - 임포트 원본 CSV/JSON을
  일반 포인트클라우드 리더로 잘못 읽으면 편차 컬럼(`Signed_Distance_mm`)이 통째로 무시되어
  결함이 사라진 채 전 셀이 "적합"으로 재판정되고, 그 오답이 현재 분석으로 승격되어 **흔적 없이
  조용히 틀리는** 문제가 있었다`[구현: dashboard/components/reanalyze-button.tsx]`

### 5.2 합성 데이터 정확도 실측

설계 정본 §12의 성공 기준은 **직선자 값 오차 ±1mm 이내, 결함 위치 셀 1칸 이내**다.

8m x 6m 합성 평탄 바닥 중앙에 **12mm 함몰**을 주입하고 노이즈 없이 분석한 결과
`[실행 확인]`:

| 항목 | 값 |
|---|---|
| 주입한 결함 깊이 (정답) | 12.00 mm |
| 측정된 최대 편차 | **11.48 mm** (함몰 반경 0.3m) / **11.81 mm** (반경 0.5m) |
| 오차 | 0.52 mm / 0.19 mm |
| 판정 분포 (48셀) | 적합 36 / 경계 12 / 보수 0 / 재시공 0 |
| **±1mm 게이트** | **충족** |

> 정답 산정 주의: "직선자 값"의 정답은 결함 높이가 아니라 지지선 기하를 반영한 포락선 해석값이다.
> 함몰·단차는 지지점이 주변 바닥이므로 해석값 = 깊이지만, 볼록 결함(범프)은 직선자가 정점에
> 얹혀 실제 높이보다 작게 읽힌다(실물 직선자도 동일). ±1mm 정밀 게이트는 함몰·단차 픽스처로
> 검증하고, 볼록 픽스처는 포락선 해석값 기준으로 단언한다.

### 5.3 성능·메모리 실측

설계 정본 §5.2의 제약은 **3천만 점을 5분 이내, 피크 메모리 증가 2GiB 이내**다.

30,000,000점 binary PLY(30m x 20m, 점 간격 약 4.5mm)를 생성해 `analyze_floor`를 실행한 결과
`[실행 확인]`:

| 항목 | 측정값 | 게이트 | 판정 |
|---|---|---|---|
| 처리 시간 | **30.2 초** | 300 초 | 충족 (게이트의 10%) |
| 피크 RSS 증가 | **1.31 GiB** | 2 GiB | 충족 (게이트의 66%) |
| 판정 셀 / 유효 셀 | 600 / 600 | - | - |
| 인식률(coverage) | 100.0% | - | - |

> **처리 시간은 재실행마다 변동한다.** 같은 PC에서 확인된 값은 33.0초(P1d 단계 기록) /
> 39.6초(직전 판) / 30.2초(본 갱신 시 재실행)로 **30~40초 범위**에서 흔들리며, 실행 환경
> 부하에 좌우된다. 반면 **피크 메모리는 1.31~1.34 GiB로 거의 일치**하며 어느 측정도 게이트를
> 넘지 않는다. 위 표는 본 갱신 시점 재실행값이다. 모든 측정이 개발용 Windows PC에서 수행됐으며,
> 목표 사양인 1 vCPU / 2GB 인스턴스에서의 측정이 아니다.

메모리가 게이트의 약 2/3인 것은 여유가 크지 않다는 뜻이다. 서브셀 정렬 기반 중앙값이 점당 약
12바이트를 쓰므로(3천만 점 = 약 360MB) 점 수가 더 늘면 선형으로 증가한다.

### 5.4 노이즈 민감도 실측 (가장 중요한 검증 결과)

**본 시스템의 판정 정확도는 스캔 품질에 지배된다.** 결함이 전혀 없는 완전 평탄면에 노이즈만
주입한 실측 결과다`[실행 확인, 기준 floor-kcs-exposed 3m/7mm, U=5mm, 48셀]`.

| 주입 노이즈 (표준편차) | 측정 최대 편차 | 측정 평균 편차 | 판정 (적합/경계/보수/재시공) |
|---|---|---|---|
| 0 mm | 0.00 mm | 0.00 mm | 48 / 0 / 0 / 0 |
| 0.5 mm | 1.52 mm | 1.35 mm | 48 / 0 / 0 / 0 |
| **1.0 mm** | 3.04 mm | 2.71 mm | **0 / 48 / 0 / 0** |
| 2.0 mm | 6.07 mm | 5.41 mm | 0 / 48 / 0 / 0 |
| 3.0 mm | 9.11 mm | 8.11 mm | 0 / 48 / 0 / 0 |

- 측정 편차는 노이즈 표준편차의 **약 3.0배로 일정하게** 나타난다(네 행 모두 배율 3.03~3.04)
- **노이즈 1mm에서 이미 결함 없는 평면 전체가 "경계"가 된다**
- 원인은 구조적이다: 직선자 포락선이 **최대** 틈새를 취하므로 무작위 노이즈가 상쇄되지 않고
  그대로 편차로 계상된다

12mm 함몰을 넣은 경우도 같은 현상이 확인된다`[실행 확인]`.

| 조건 | 측정 최대 편차 | 판정 (적합/경계/보수/재시공) |
|---|---|---|
| 노이즈 0 | 11.48 mm | 36 / 12 / 0 / 0 |
| 노이즈 표준편차 2mm | 15.47 mm | 0 / 44 / 4 / 0 |

노이즈는 결함을 가리는 것이 아니라 **없는 결함을 만들어낸다.** 결함이 없는 44개 셀이 경계·보수로
오염되고 최대값도 부풀었다. 위 판정 분포(36/12 및 0/44/4)는 백로그 티켓 35의 기록과 정확히
일치함을 재현으로 확인했다.

**이 결과의 함의**: 실제 모바일 LiDAR의 노이즈 수준이 2mm 근방이라면, 본 시스템은 평탄한 바닥도
전 구간 "경계"로 판정한다. 이는 오작동이 아니라 **측정 불확도를 정직하게 반영한 결과**이지만,
실용성 측면에서는 스캔 품질 개선 또는 U 재설정이 필요함을 뜻한다(6.3절).

### 5.5 판정 기준 데이터 정합성 검증

`[실행 확인]` 엔진 시드(`seed_criteria.json`) 11행과 DB 시드(마이그레이션 002) 11행이 표면·출처
문자열·metric·span·pass·rework 전 필드에서 완전히 일치함을 확인했다. 전 11건이
`rework = pass x 3` 관계를 만족한다.

동시에 다음 문제를 발견해 [`criteria-sources.md`](criteria-sources.md) 6장에 기록했다.

- 기본 U에서 적합 상한 `b1 = pass - U`가 **0 이하**가 되어 완전 평탄면조차 "적합" 판정이
  원리적으로 불가능한 기준 **3종** (`wall-kcs-tilt-exposed` -2.0mm, `wall-plaster-surface`
  -5.0mm, `wall-plaster-base` -2.0mm). **벽면 평활도 기준 4종 중 3종**이며, 정상인 1종
  (`wall-kcs-tilt-other`)조차 여유가 1mm뿐이다
- `wall-plaster-surface`는 `pass + U >= rework`라 보수 구간이 소멸하고
  `uncertainty_swallows_repair` 경고가 상시 발생
- 설계 정본 §4.1이 기록한 `wall-kcs-plumb`의 "노출 모서리 13mm" 변형이 엔진·DB 시드 어디에도
  없다(조건별 행 분리 규정의 누락)

**조치(본 갱신에서 반영)**: 첫 번째 항목은 이전까지 화면·보고서 어디에도 드러나지 않아 사용자가
"왜 적합이 하나도 없는지" 알 수 없었다. 신규 경고 코드 **`uncertainty_swallows_pass`** 를
추가해 `b1 <= 0`인 기준/불확도 조합에서 자동으로 경고와 한국어 해설이 붙도록 했다
`[구현: engine/flatness/criteria.py]`. **다만 이는 가시화이지 해소가 아니다** - 근본 해소는 U를
실측 재현성으로 갱신하는 것이며(6.3절, 미수행), 백로그 티켓 47로 관리한다. 세 번째 항목은
시드 행 추가만으로 끝나지 않아(수직도 기준이 `core/walls.py`에 고정 조회됨) 티켓 46으로
분리했다.

## 6. 한계와 후속 과제

### 6.1 iPhone LiDAR 스크리닝 도구로서의 근본적 한계

**본 시스템은 합격/불합격을 확정하는 공식 검측 도구가 아니다.** 이는 구현의 미비가 아니라
장비 특성에서 오는 원리적 한계이며, 설계 초기부터 명시적으로 포지셔닝한 사항이다.

학술 문헌 조사에 따르면 iPhone LiDAR 점군의 상대 거리 오차는 방 규모에서 약 3cm(수직 방향은
±7mm 수준), SLAM 드리프트는 이동거리의 1~2%다. **시방서 허용오차(3m당 3~10mm)와 같은
자릿수이거나 이를 초과한다.**

따라서 본 시스템은 다음을 강제한다.

- 판정을 4등급으로 나누고 불확도 구간을 **"경계(현장 재확인 필요)"** 로 분리
- 모든 결과·보고서에 측정 불확도 수치와 **"본 결과는 스크리닝이며 공식 검측(실물 직선자·레벨
  측량)을 대체하지 않습니다"** 문구를 자동 포함
- 판정 불가 셀에 수치를 강제로 산출하지 않고 "판정 불가"로 명시 출력

**실무 활용 방식**: 전수 스크리닝으로 의심 구간을 좁힌 뒤, 그 구간만 실물 직선자로 정밀
검측하는 2단계 운용이 본 시스템이 의도한 사용법이다.

### 6.2 실측 대조 미수행 (가장 중요한 미완 항목)

**실제 현장에서 실물 3m 직선자로 측정한 값과 본 시스템의 판정값을 대조하는 검증이 수행되지
않았다.** 설계 정본 §10.4가 이를 릴리스 게이트로 규정했으나 충족하지 못했다.

- **미수행 사유**: 실제 시공 현장 접근과 검측 장비(3m 직선자·레벨)가 필요하며, 본 개발 범위
  내에서 확보되지 않았다
- **영향**: 5.2절의 정확도 실측은 **합성 데이터**에 대한 것이다. 합성 데이터는 노이즈 모델이
  가우시안이고 공간적으로 무상관이지만, 실제 LiDAR 노이즈는 그렇지 않을 수 있다. 따라서
  **실제 현장에서의 정확도는 알려져 있지 않다**
- **필요 조치**: 현장 1곳 이상에서 동일 구간을 실물 직선자로 측정하고 셀 단위로 대조해 상관을
  보고해야 한다. 이 대조 없이는 본 시스템의 판정값을 공식 검측 근거로 사용할 수 없다

### 6.3 노이즈 민감도 (백로그 티켓 35)

5.4절의 실측대로 **스캔 노이즈가 판정을 지배한다.** 노이즈 표준편차 2mm(실제 모바일 LiDAR
수준으로 추정)에서 평탄면이 전 구간 경계로 판정된다.

구조적 원인: 직선자 포락선이 최악값을 취하므로 랜덤 노이즈가 그대로 편차로 계상된다.

**대응 후보** (어느 것도 아직 채택·구현되지 않음)
1. 서브셀 집계 강화 (중앙값 창 확대)
2. 포락선에 강건 백분위 적용 (최대값 대신 상위 백분위)
3. **U를 실측 재현성으로 재설정** (설계 정본 §4.2가 예정한 작업)

3번이 가장 원칙적이나 6.2절의 실측이 선행되어야 한다. 1·2번은 실물 직선자와의 등가성을 훼손할
수 있어(실물 직선자도 최악값을 본다) 신중한 검토가 필요하다.

### 6.4 판정 기준의 검증 상태

[`criteria-sources.md`](criteria-sources.md)에 상세히 기록했으며 요지는 다음과 같다.

- **시방서 원문을 직접 열람해 대조한 기준은 0건이다.** 전 11건이 2차 출처 교차검증 수준이며,
  그중 5건은 조항 번호·표 번호·현행 승계 여부까지 미확정이다
- 판정식의 4등급·측정 불확도·축소 스팬 환산·재시공 임계는 **시방서에 없는 본 시스템의 해석**이다
- 측정 불확도 U(바닥 5mm, 벽 8mm)는 **실측 근거가 없는 잠정치**다
- 기본 U에서 적합 판정이 원리적으로 불가능한 기준이 3종 존재한다

**발주처 제출물·논문에 기준 수치를 인용하기 전 원문 대조가 필수다.**

## 7. 활용 방안과 세부과업 2 연계

### 7.1 현장 활용 시나리오

1. **시공 중 전수 스크리닝** - 마감 전 바닥·벽면을 LiDAR로 전수 스캔해 의심 구간을 조기 발견한다.
   실물 직선자로 전수 검사하는 것보다 훨씬 빠르며, 본 시스템의 강점이 가장 잘 드러나는 용도다
2. **검측 대상 구간 선별** - 스크리닝 결과 "보수"·"재시공"으로 나온 구간만 실물 직선자로 정밀
   검측한다. 6.1절의 2단계 운용이다
3. **시공 이력 축적** - 현장·동·층·공간·측정위치 체계로 결과가 누적되어 시공사·공정별 품질
   경향을 비교할 수 있다
4. **보수 물량 산정** - 셀 단위 판정과 결함 위치 좌표로 보수 면적을 **산정할 수 있다.**
   단 **자동 면적 집계는 구현되어 있지 않다**(6.5절, 설계 정본 §5.1.7). 현재는 등급별 셀 수와
   구역 면적(`zones[].area_m2`)에서 사용자가 환산해야 한다. 정밀 편차맵은 "어디를 얼마나 갈아야
   하는가"를 평면 도면처럼 보여준다

### 7.2 세부과업 2(마감재 DB) 연계 구조

세부과업 2는 본 과업의 범위 밖이지만, **평활도 판정 결과가 마감재 선정의 입력이 되도록**
데이터 구조를 준비해 두었다.

**연계의 논리**: 마감재는 바탕면 상태에 따라 시공 가능 여부와 필요 두께가 달라진다. 얇은
마감(제물치장·도장·벽지)은 평탄한 바탕을 요구하고, 두꺼운 마감은 요철을 흡수한다. 본 시스템의
판정 기준 자체가 이미 이 관계를 반영하고 있다.

| 본 시스템의 기준 | 대응하는 마감 조건 |
|---|---|
| `floor-kcs-exposed` (3m/7mm) | 제물치장·얇은 마감 |
| `floor-kcs-finish7plus` (1m/10mm) | 마감두께 7mm 이상 |
| `floor-lh-exposed` (3m/6mm) | 제물치장·도장·벽지 바탕 |
| `floor-lh-thick` (3m/10mm) | 마감두께 13mm 초과 |

**즉 판정 기준과 마감재 종류가 이미 1:1로 대응한다.** 세부과업 2는 이 대응을 역방향으로 쓰면
된다: 측정된 바닥 상태로부터 **시공 가능한 마감재 목록**을 역산하는 구조다.

**연계 지점으로 사용 가능한 데이터**

| 데이터 | 위치 | 마감재 DB에서의 용도 |
|---|---|---|
| 측정위치별 종합 판정 | `analyses.overall_verdict` | 해당 공간의 "바닥 상태 등급" |
| 등급별 셀 수·비율 | `analyses.stats.grade_counts` / `grade_pct` | 부분 보수 후 시공 가능 여부 판단 |
| 최대·평균·95백분위 편차 | `analyses.stats.value_*` | **어느 두께의 마감재까지 시공 가능한지 직접 역산** |
| 셀별 편차와 좌표 | `cells.json` / `results.csv` | 구간별로 다른 마감을 적용할 때의 경계 산정 |
| 적용 기준 스냅샷 | `analyses.applied_criteria` | 판정의 근거가 된 기준을 추적 |
| 측정위치 계층 | `locations` (동·층·공간) | 마감재 물량 산정 단위와 직접 결합 |

**연계 방식 제안**: `analyses`를 참조하는 별도 테이블로 마감재 적합성을 기록하면, 본 시스템의
스키마를 수정하지 않고 확장할 수 있다. `analyses.stats`가 jsonb이고 계약 문서가 정본으로
관리되므로(`docs/contracts/stats-schema.md`) 소비자가 안정적으로 읽을 수 있다.

### 7.3 세부과업 3~4를 위해 유지한 것

- **데이터 포맷**: LAS/LAZ 지원으로 지상 레이저 스캐너(TLS) 데이터도 동일 파이프라인으로 처리
  가능하다. BIM 연계 시 좌표계 정합에 유리하다
- **좌표 프레임 계약**: 바닥 절대좌표와 벽 (u,v) 프레임의 3D 역매핑 공식이 계약 문서에
  규정되어 있어, BIM 모델 좌표계로의 변환 경로가 열려 있다
- **구배 알고리즘(세부과업 4) 관련**: 구역별 평면 계수(`zones[].plane_abc`)가 이미 산출되고
  저장되므로 설계 구배와의 대조에 바로 쓸 수 있다. 다만 현재는 판정이 **평면 제거 후 국부
  요철**만 보므로, 구배 자체의 적정성 판정은 별도 로직이 필요하다

## 8. 결론 (세부과업 1)

> 이 장은 **세부과업 1의 결론**이다. 세부과업 4의 결론은 9.9절에 따로 있다.

과업지시서 세부과업 1이 요구한 성과물 가·나·다 항목을 **미이행 0건**으로 구현했고, 본 문서로
라 항목을 제출한다. 자동화 테스트 628건이 통과하며, 합성 데이터에서 ±1mm 정확도 게이트와
3천만 점 성능 게이트를 모두 충족한다.

동시에 다음을 분명히 밝힌다.

1. **실물 직선자를 이용한 현장 실측 대조는 수행되지 않았다.** 5.2절의 정확도는 합성 데이터에
   대한 것이며, 실제 현장에서의 정확도는 검증되지 않았다
2. **시방서 원문을 직접 대조한 판정 기준은 0건이다.** 전 11건이 2차 출처 교차검증 수준이다
3. **측정 불확도 U는 실측 근거가 없는 잠정치다**
4. **스캔 노이즈가 판정을 지배한다.** 노이즈 표준편차 1mm에서 이미 결함 없는 평면이 전 구간
   "경계"로 판정됨을 실측으로 확인했다
5. **벽면 판정은 현재 실질적으로 "경계 이상"만 산출한다.** 탑재된 벽면 평활도 기준 4종 중
   3종이 기본 U=8mm에서 적합 판정이 원리적으로 불가능하며(5.5절), 나머지 1종도 여유가 1mm뿐이다.
   시스템은 이 상태를 `uncertainty_swallows_pass` 경고로 표시하지만, 해소는 3번(U 확정)에
   달려 있다. **벽면 결과를 읽을 때 이 점을 반드시 감안해야 한다**(백로그 티켓 47)

1~3번은 현장 접근과 원문 확보라는 외부 조건이 필요한 항목이며, 4·5번은 1번의 결과에 따라 대응
방안을 결정해야 하는 항목이다. **본 시스템을 공식 검측 근거로 사용하려면 위 네 항목의 해소가
선행되어야 하며, 그 전까지는 설계 의도대로 스크리닝 도구로만 운용해야 한다.**

### 9.1 과업 개요

#### 9.1.1 목적

과업지시서 10~12쪽의 세부과업 4에 대응한다. 점군에서 **2m x 2m 격자 단위로 바닥 구배(물매)를
자동 산출**하고, 용도별 설계 기준과 대조해 판정하며, 여러 위치에서 나눠 찍은 스캔을 하나로
**정합**해 중첩 영역을 보완한다.

세부과업 2·3보다 4를 먼저 수행한 이유는 두 가지다`[스펙(구배·정합) §1.1]`. 세부과업 1의 엔진과
기술 스택을 거의 그대로 재사용할 수 있고, 2·3과 달리 Revit 라이선스·C# 환경·BIM 모델 샘플 같은
외부 의존성이 없어 즉시 착수할 수 있었다.

#### 9.1.2 범위

**포함**
- 2m x 2m 격자 구배 산출 (크기 %, 내리막 방향, 피팅 잔차, **셀별** 불확도)
- 용도별 설계 구배 기준 5종 탑재와 4등급 판정 (역구배 포함)
- 배수구 위치를 결과 화면에서 클릭해 방향 판정·재판정
- 최적 보정 방향과 보정 높이차(mm) 산출
- 구간별 구배 편차 통계 (평균·표준편차·최대편차). **"구간"의 해석은 9.5절**
- 멀티 소스 반자동 정합과 병합 스캔 생성
- 산출물 CSV·PNG·JSON 5종

**제외**`[스펙(구배·정합) §11]`
- 드론·터틀봇 **실물 데이터 연동**. 반자동 정합은 대응점만 있으면 소스를 가리지 않으므로
  알고리즘은 데이터에 무관하다. 실물이 확보되면 검증만 추가하면 된다
- 대응점 **자동 특징 매칭**. 드론·지상 데이터는 중첩 특징이 약해 신뢰하기 어렵다
- 옥외 대면적 성능. 세부과업 1의 성능 게이트(3천만 점, 5분, 2GiB)를 그대로 쓴다

**범위 안이었으나 단계 G까지 이행하지 못했다가 단계 H에서 채운 것**
- **구배 분석 결과의 자동 PDF 보고서 편입.** 보고서 후보 선택부터 컨텍스트 적재·자산 복사·

따라서 **과업지시서가 요구한 산출 형식 3종(CSV·PNG·PDF)이 모두 채워졌다.** 다만 다음 둘은
과장하지 않고 남긴다.

- **리눅스 컨테이너에서의 한글 렌더는 여전히 미검증이다.** 위에서 확인한 것은 **개발 PC의
  Windows 로컬 Chromium**이며, 배포 컨테이너(`fonts-noto-cjk`)의 실제 렌더는 **배포 후
  스모크가 최초 검증**이다(9.7절 한계 12, [`DEPLOY.md`](DEPLOY.md) §4)
- **`slope_map.png` 자체의 한글**(엔진 matplotlib 산출물)은 위 렌더 확인의 범위 밖이다.
  육안 확인에 쓴 PNG는 테스트가 만든 대체물이고, 지도 안의 한글 라벨은 히트맵과 같은
  matplotlib 폰트 경로를 타므로 6.6절 티켓 37과 같은 조건에 걸린다
- **구배 등급은 PDF에서 색 없이 문구로만 구별된다**(화면의 색 히트맵과 인상이 다르다).
  의도적 선택이다 - 구배 색표는 엔진 `outputs/slope_map.py`와 대시보드
  `slope-heatmap.ts` 두 곳에 있는데, 스냅샷에 실으면 **대조 장치 없는 세 번째 사본**이
  생긴다. 이 저장소가 반복해 겪은 사고가 정확히 그것이다(`labels.py`가 `labels.ts`를
  파싱해 대조하는 장치를 두는 이유). 스펙 §7.2가 어차피 "역구배를 색만으로 구별하지
  말 것"을 요구하므로 등급명·`(역구배)` 배지·사유 문구로 구별한다. **정보 손실은
  없고**, 색이 필요하면 대조 테스트와 함께 넣어야 한다

#### 9.2.1 기술 사양 이탈에 대한 상시 방침

**원칙.** 과업지시서가 지정한 **기술 사양(사용 언어·라이브러리·소프트웨어·알고리즘 구현
방식)은 구속력 있는 요구가 아니라 참고**로 취급한다. 같은 목적을 더 낫게 달성하는 대안이
있으면 그것을 채택하고, **왜 그렇게 했는지를 본 보고서에 밝힌다.** 발주처가 상시 방침으로
확정했다(2026-08-09).

> "과업지시서를 모두 그대로 받아들이지 말고 좀 더 좋은 대안이 있으면 그렇게 진행하면 된다.
> 나중에 왜 그렇게 했는지만 이야기하면 되는 것이다. 거기서 말한 사용 컴퓨팅 언어나
> 소프트웨어 등은 그대로 안 따라가도 된다."

3.2절이 Open3D·PCL 미채택을 "사용자 승인"으로 기록한 것은 **단발 예외처럼 읽히지만, 실제로는
이 방침의 첫 적용 사례다.** 그래서 이 절에 방침과 적용 사례를 한곳에 모은다.

**구속력이 있는 것과 없는 것.** 이 구분이 방침의 핵심이다.

| 구분 | 항목 | 취급 |
|---|---|---|
| **구속력 없음** | 사용 언어 · 라이브러리 · 소프트웨어 · 알고리즘 구현 방식 | 더 나은 대안을 채택하고 근거를 밝힌다 |
| **구속력 있음** | **산출물과 그 형식**(CSV · PNG · PDF) | 발주처가 실제로 받는 결과물이다 |
| **구속력 있음** | **정밀도 사양**(11쪽 분석 오차율 ±5% 이내, 이 용역이 상대하는 ±5mm 평탄 바닥) | 판정의 의미가 여기에 걸려 있다. 9.6.2절이 실측으로 대조한다 |
| **구속력 있음** | **분석 단위**(2m x 2m 격자) | 결과를 읽는 기준 좌표다 |
| **구속력 있음** | **산출 항목**(구배값 · 설계기준 대비 편차 · 평균편차 · 표준편차 · 최대편차) | 발주처가 원문과 대조할 목록이다 |

**단계 H에서 구배 PDF를 구현하는 이유가 정확히 이 구분이다.** 도구는 자유롭게 골랐지만
(아래 표), 과업지시서 11·12쪽이 명시한 산출 형식 3종 중 PDF가 비어 있는 것은 **이탈이 아니라
미이행**이다. 산출물 형식은 발주처가 받는 결과물이라 이탈 대상이 아니므로, 도구 선택은 그대로
두고 빠진 산출물만 채운다.

**적용 사례 전수.** 지금까지의 기술 사양 이탈을 한곳에 모았다. 각 행은 이미 본문 어딘가에
기록돼 있던 것이며, 여기서는 근거와 나란히 놓아 발주처가 한 번에 판단할 수 있게 했다.

**이 방침이 바꾸지 않는 것.** 위 6건은 **"같은 목적을 더 나은 수단으로 달성했다"** 는 기록이며,
**미이행·미검증 항목을 지우거나 완화하지 않는다.** 9.2절의 부분 이행 4건, 9.7절의 한계 14건,
9.6절이 밝힌 미수행 검증은 이 방침과 무관하게 그대로 남는다. 특히 다음 둘은 **이 표에 넣지

- **정합 복원 게이트 교체**(9.6.3절). 도구 선택이 아니라 **검증 기준을 바꾼 일**이다. 원 게이트가
  달성 불가능함을 실측으로 보인 뒤 목적 적합성 기준으로 교체했고, **회전 오차가 게이트에서
  빠졌다는 사실을 한계 1로 남겨 두었다.** 방침을 이유로 이것을 이탈로 재분류하지 않는다
- **전처리(복셀 다운샘플·아웃라이어 제거·바닥 조건별 전처리) 부재**(9.2절 부분 이행). 더 나은
  대안을 고른 것이 아니라 **구현하지 않은 것**이다

### 9.3 구현 내용

#### 9.3.1 구배 산출 알고리즘

서브셀 격자(5cm)는 평활도와 공유하고 **집계 단위만 2m로 바꾼다.** 2m 셀 하나가 40 x 40
서브셀이다`[구현: engine/flatness/core/slope.py compute_slope_cells]`.

**셀별 평면 피팅은 원점군이 아니라 서브셀 중앙값에 한다.** 이유는 셋이다`[스펙(구배·정합) §4.2]`.

1. 노이즈가 중앙값 단계에서 이미 걸러진다
2. 점 밀도 불균일의 영향이 사라진다. 원점군에 그대로 피팅하면 스캐너에 가까워 점이 빽빽한
   구역이 평면을 끌어당긴다. 서브셀 중앙값은 면적당 균등하다
3. 계산량이 수천분의 1이다

평면 `z = a·x + b·y + c`에서 다음을 얻는다.

| 산출값 | 식 |
|---|---|
| 구배 크기(%) | `sqrt(a² + b²) x 100` |
| **내리막 방향(rad)** | **`atan2(-b, -a)`** |
| 피팅 잔차 RMSE | 셀 안 **모든 유효 서브셀**에 대한 잔차 (인라이어만이 아니다) |
| 기울기 표준오차(%) | `100 x hypot(rmse/(sqrt(N)·sd_x), rmse/(sqrt(N)·sd_y))` |

**부호 반전은 설계 정본의 오류를 정정한 것이다.** `(a, b)`는 **오르막** 방향 벡터인데, 물은
내리막으로 흐르므로 배수 방향 판정은 내리막 기준이어야 한다. 설계 정본 초판 §4.2는
`구배 방향(rad) = atan2(b, a)`로 적혀 있었고`[커밋 635ba2a 시점 원문]`, 그대로 구현했다면
**모든 방향 판정이 180도 뒤집혀 정상 배수가 전부 역구배(재시공)로 나왔을 것이다.** 단계 B의
구현 계획이 이를 잡아 코드와 스펙을 함께 고쳤다`[커밋 78e2f99 "2m 격자 구배 산출 + 스펙의
방향 부호 오류 정정"]`.

**가장자리 조각 셀은 판정에서 뺀다.** 폭이든 높이든 `cell_m/2`(= 1m) 미만이면 baseline이
짧아 서브셀 중앙값의 실제 위치와 가정한 중심의 불일치가 평균되지 않고 **편향으로 남는다.**
개수 검사(유효 서브셀 10개 이상)만으로는 이것을 못 걸러낸다`[구현: core/slope.py]`. 현장에서는
**판정하려는 구역을 2m 단위로 여유 있게 덮어 스캔해야** 자투리가 통째로 빠지지 않는다
([`scan-guideline.md`](scan-guideline.md) 10.1절).

#### 9.3.2 판정 규칙 - 불확도를 감안해도 확실할 때만 단정한다

기호: `g` = 실측 구배(%), `u` = 셀별 표준오차(%), `d = |g - design_pct|`, `θ` = 실측 내리막
방향과 기대 방향(셀 중심에서 가장 가까운 배수구를 향하는 방향)의 각도 차.

1. **판정 불가 걸러내기.** 유효 서브셀 10개 미만, 격자 가장자리 조각 셀, 또는 `u > pass_pct`
   (허용치보다 불확도가 커서 가릴 해상도가 없는 셀). 사유를 구분해 남긴다
2. **역구배 우선.** `θ > 90도`이면 크기와 무관하게 **재시공**이고 여기서 끝난다
3. **재시공.** `d - u > re_pct`
4. **적합.** `d + u <= pass_pct` **그리고** `θ <= dir_pass_deg`
5. **보수.** `d - u > pass_pct` 또는 `θ > dir_pass_deg`
6. **경계.** 위 어디에도 확정적으로 걸리지 않는 셀

`u`를 더하고 빼는 방향이 이 규칙의 핵심이다. **적합은 불확도를 감안해도 확실히 안쪽일 때만
주고(`d + u`), 재시공은 불확도를 감안해도 확실히 바깥일 때만 준다(`d - u`).** 그 사이는 경계로
남긴다 - 데이터가 단정을 허락하지 않는데 단정하면 안 된다`[구현: core/slope.py grade_slope_cells]`.

**역구배 검사는 `dir_pass_deg` 설정값과 무관하게 90도 고정이다.** 따라서 방향 판정 대상이
아닌 기준(`slope-indoor-level`, `dir_pass_deg=180`)으로 분석할 때 배수구를 지정하면 수평
바닥의 무작위한 미세 기울기 때문에 절반가량이 재시공으로 찍힌다. `dir_pass_deg`를 180으로
두어도 이 경로는 막히지 않는다([`slope-criteria-sources.md`](slope-criteria-sources.md) 2.5절).
화면은 방향을 판정하지 않는 기준에서 배수구 클릭을 비활성화하고 그 이유를 표시한다
`[구현: dashboard/components/analysis/slope-result.tsx]`.

**불확도가 전역 상수가 아니라 셀별이라는 점이 평활도와 다르다.** 평활도는 전역 `U`(바닥 5mm,
벽 8mm)를 쓰고, 그 탓에 벽면 기준 4종 중 3종이 적합 판정 자체가 원리적으로 불가능해지는 문제가
있다(5.5절·6.4절, 백로그 티켓 47). 구배는 최소제곱 평면 피팅이 기울기 계수의 표준오차를 직접
주므로 **데이터가 좋은 셀은 좁은 불확도로 단정하고 나쁜 셀만 경계·판정 불가로 빠진다.**
같은 종류의 부정합이 구조적으로 생기지 않는다`[스펙(구배·정합) §4.3]`.

**보정 방향**은 실측 벡터에서 설계 벡터를 뺀 것이며, %로만 보여주면 시공자가 쓸 수 없으므로
**양단 높이차(mm)로 환산한다**: `correction_mm = d x min(셀 폭, 셀 높이) x 10`. 명목 2m가
아니라 셀의 실제 폭·높이를 쓰는 이유는, 가장자리에서 다소 잘린 셀의 보정량이 과대 보고되지
않게 하기 위해서다`[구현: core/slope.py]`.

#### 9.3.3 정합 - 반자동 대응점 + Umeyama + trimmed ICP

| 단계 | 내용 |
|---|---|
| 입력 | 두 스캔의 높이 뷰에서 사람이 찍은 대응점 **3쌍 이상**. 화면 안내는 **"최소 3쌍이 필요하고 4쌍 이상을 권장합니다."** 다`[구현: dashboard/components/registration/registration-workbench.tsx]` |
| 1단계 | **Umeyama/Kabsch 닫힌 해**로 강체 변환 계산. **축척은 고정**한다 - 축척까지 추정하면 단위 오입력을 정합이 조용히 흡수해 오류가 안 보인다 |
| 2단계 | **trimmed point-to-point ICP**(`trim_ratio=0.8`, 대응 탐색 SciPy `cKDTree`)로 정밀화 |
| 수렴 | 직전 반복 대비 RMSE 변화율 `< 1e-4` 또는 최대 반복 50회 |
| **보고값·성공 임계** | **point-to-plane 잔차** `<= 2mm``[구현: engine/flatness/core/registration.py MAX_RMSE_M=0.002]` |

**잔차를 두 가지로 나눠 쓰는 것이 이 구현의 핵심 결정이다.** 최소화와 수렴 판정은
point-to-point로 하고, **보고값과 성공 임계만 point-to-plane**으로 한다. 이유는 실측에 있다.
point-to-point 잔차에는 **표본 간격 절반 수준의 하한**이 있어서, 두 스캔이 같은 표면을 서로
다른 점으로 표본하면 접선 방향 어긋남이 잔차에 그대로 섞인다. 표본 간격 5cm에서 실측
point-to-point RMSE는 **19.50mm**로, 정합이 정확한데도(z 오차 0.008mm) 2mm 게이트를 못 넘는다.
그것은 정합 품질이 아니라 **격자 해상도의 그림자**이며, 실제 병합 입력이 5cm 서브셀 중앙값
점군이므로 **현장에서 모든 정합이 실패로 보고될 위험이었다.** point-to-plane으로 바꾸면 같은
정합이 **1.047mm**로 통과한다`[스펙(구배·정합) §9.3.1]`.

**실행 시 엔진이 실제로 거르는 것은 다음뿐이다**`[구현: core/registration.py]`.

| 게이트 | 임계 |
|---|---|
| 최종 RMSE (point-to-plane) | `> 2mm`이면 실패 |
| 중첩 부족 | `overlap_ratio < 0.1`. **trim이 상한이라 참 중첩 12.5% 미만을 거른다**(9.7절 한계 7) |
| 대응점 회전 불확도 | `σ_θ = σ_click / sv1 > 60도`이면 거부 (`CORR_CLICK_SD_M = 0.05`) |
| 대응점 퍼짐 | 최대 퍼짐이 정합 영역 대각의 **12% 미만**이면 거부 (`MIN_CORR_SPREAD_FRACTION = 0.12`) |
| 발산 가드 | `point_rmse_m > 1.5 x 표본 간격` |
| 수렴 실패 | `converged=False` |

> **z 오차 1mm는 실행 시 게이트가 아니다.** 이 문서와 가이드라인이 여러 곳에서 인용하는
> "z <= 1mm"는 **`engine/tests/test_registration.py`의 회귀 시험 기준**이다. 엔진 실행 경로에는
> `MAX_RMSE_M = 0.002`만 있고 **z는 따로 검사하지 않는다**`[구현: core/registration.py에 z 임계
> 상수 없음]`. 이 구분을 지키지 않고 "게이트"라고 쓰면 거짓 서술이 된다. 실제 결과는 9.6.4절
> (e) 표대로, 구배 20% 구간까지 전부 `converged=True`가 나온다.

**대응점 기하 검사는 개수가 아니라 배치를 본다.** 판별을 무차원 비(`sv1/sv0`)가 아니라
**절대량**으로 하는 이유는, 무차원 비가 실효적으로 "대응점 배치 종횡비"를 재게 되어 **물리적으로
더 좋은 배치를 거부하고 더 나쁜 배치를 통과시키기** 때문이다. 예를 들어 150m x 2.5m 복도의
대응점 배치는 `sv1/sv0`가 0.0163으로 최악처럼 보이지만 실제 면내 오차는 37.5mm로 정상 4점 배치
(0.6695 / 44.7mm)보다 **좋다**`[스펙(구배·정합) §9.3.3]`.

#### 9.3.4 병합 - 서브셀 중앙값 점군

병합 산출물을 **5cm 서브셀 중앙값 점군**으로 만들어 두 문제를 동시에 푼다`[스펙(구배·정합) §6.3]`.

- **중첩 영역 보완**(과업지시서 명시 항목): 중첩 서브셀에 두 소스의 점이 함께 들어가고 중앙값이
  뽑히므로, **별도 가중치 설계 없이 이상치에 강하게** 통합된다
- **파일 크기**: 두 점군을 그대로 이어붙이면 Storage 버킷의 50MB 상한(3.5절)에 걸린다. 5cm 서브셀
  중앙값이면 600 m² 바닥이 약 24만 점, **3MB 수준**이다. 분석은 어차피 서브셀 중앙값만 쓰므로
  **판정 결과가 동일하다**

원본 두 스캔은 그대로 남고 `registrations` 행이 소스와 결과를 잇는다. 병합 스캔의 데이터 계보는
`registered`("정합 병합")이며 **업로드 화면에서 고르는 값이 아니라 시스템이 붙이는 값**이다
`[구현: dashboard/lib/domain/labels.ts]`. 두 소스는 **순차로** 처리한다 - 서브셀 격자의 정렬
버퍼가 점당 약 12바이트라 두 개를 동시에 들면 피크 메모리가 두 배가 된다
`[구현: worker/flatworker/registration.py]`.

엔진과 브라우저 두 곳에 생기고, 세부과업 1에서 같은 종류의 이중화가 실제로 어긋난 전례가

화면은 스캔 상세의 **"구배 분석"** 버튼(기준 선택 UI 포함), 구배 결과 화면(4등급 히트맵 +
방향 화살표 오버레이 + 셀별 결과표 + 통계), **배수구 클릭 재판정**, 정합 화면(대응점 클릭 ->
정합 실행 -> 겹쳐보기 -> 병합 스캔 열기)으로 구성된다`[구현: dashboard/components/analysis/
slope-*.tsx, dashboard/components/registration/*.tsx]`. 절차의 상세는
[`scan-guideline.md`](scan-guideline.md) 9.2·10.2절에 현장 담당자용으로 적었다.

|---|---|---|---|---|---|---|---|---|
| 1 | `slope-roof-exposed` | 옥상 슬래브 (노출방수) | 3.5 | 1.5 | **2.0 ~ 5.0%** | 4.5 | 1/50~1/20 = 2~5% | A |
| 2 | `slope-roof-protected` | 옥상 슬래브 (비노출·보호층) | 1.5 | 0.5 | **1.0 ~ 2.0%** | 1.5 | 1/100~1/50 = 1~2% | A |
| 3 | `slope-bathroom` | 욕실·화장실 바닥 | 0.5 | 0.5 | **0.0 ~ 1.0%** | 1.5 | 1/100 이하 | A |
| 4 | `slope-parking` | 주차장 바닥 | 1.5 | 1.5 | **0.0 ~ 3.0%** | 4.5 | 가로방향 3% 이하 | A (**상한만**) |
| 5 | `slope-indoor-level` | 실내 평바닥 | 0.0 | 1.0 | **0.0 ~ 1.0%** | 3.0 | **없음** | C |

**이 표의 수치는 근거의 성격이 세 가지로 갈린다. 섞어서 인용하면 안 된다.**

- **설계 구배(`design_pct`)와 적합 폭(`pass_pct`)은 인용해도 된다.** 기준 문서들은 구배를
  점값+공차가 아니라 **범위**로 규정하는데(예: 1/100~1/50), 범위 `[lo, hi]`는
  `design=(lo+hi)/2`, `pass=(hi-lo)/2`와 **동치**다. 즉 표기 변환이지 창작이 아니며, "적합 구간"
  열이 원문 범위와 같은지 대조하면 확인된다. **4종이 원문 대조 완료(등급 A)**다
- **재시공 임계(`re_pct`)는 어느 기준 문서도 규정하지 않는다.** 이것은 **본 저장소의 관례인
  "적합 폭의 3배"**를 적용한 값이다. 평활도 기준 11종이 예외 없이 `재시공 = 허용치 x 3`을 쓰고
  있고(KCS 14 20 10 표 3.7-1에서 온 비율) 구배도 같은 비율을 적용했다. **이것은 구배에 대한
  기준 문서의 근거가 아니라 시스템 내부 일관성이다.** 인용할 때는 반드시 "본 용역이 적용한
  저장소 관례"로만 적어야 한다
- **방향 허용각(`dir_pass_deg`) 30도는 근거가 없는 용역 자체 설정값이다.** 내리막이 배수구를
  향하는 방향에서 몇 도까지 적합으로 볼 것인가를 규정한 문서를 찾지 못했다. **발주처·감리와
  협의해 조정할 값이다**

**주차장은 배수를 위한 최소 구배 기준이 존재하지 않는다.** 채택한 KDS 44 70 05 §4.1.3(3)
"주차장 내의 경사는 주차 차량의 세로방향 2%, 가로방향 3% 이하로 하고"는 **배수 최소치가 아니라
주차 안전을 위한 상한**이다(바로 다음 항이 차량 구름 방지를 말한다). 따라서 적합 구간
[0.0, 3.0]%의 **상한만 근거가 있고 하한 0.0은 "최소 구배 규정이 존재하지 않음"의 표현**이다.
게다가 이 기준은 §1.2가 적용 대상을 도로법상 도로에 설치하는 주차장 등으로 한정하므로
**건축물 부설 지하주차장은 직접 적용 대상이 아니다** - "KDS 44 70 05 준용"으로 표기해야 한다.

**역구배만은 근거가 있다.** 「공동주택 하자의 조사, 보수비용 산정 및 하자판정기준」이 '역물매가
형성된 경우'를 하자로 명시한다(등급 B, 원문 렌더링 실패로 2차 출처 확인). 그래서 역구배는
`dir_pass_deg` 설정값과 무관하게 항상 재시공이다(9.3.2절).

> **크기 등급을 그대로 "하자"로 옮기면 고시와 어긋난다.** 같은 고시는 "사용상 지장이 없을
> 정도의 부분적 물고임"과 **"옥내에서 설계 당시부터 배수 물매가 고려되지 않은 경우"**를 하자가
> 아니라고 본다. 즉 옥내(지하주차장 등)에서 설계상 배수 물매가 없었던 바닥은 구배가 미달해도
> 하자가 아니다. **본 시스템의 출력은 시공 상태의 계측 결과이며, 하자 여부는 설계도서상 배수
> 물매 표기 유무와 함께 판단해야 한다.**

### 9.5 "구간별 통계"의 해석 - 발주처 판단을 구한다

과업지시서 11쪽에 두 줄이 나란히 있다. 아래 인용은 결정 기록
[`superpowers/specs/2026-08-04-zone-stats-decision.md`](superpowers/specs/2026-08-04-zone-stats-decision.md)가
원문에서 옮겨 적은 것이며, 9.2절 서두의 단서(원문 PDF가 저장소에 없다)가 여기에도 그대로
적용된다.

> 구간별 구배 편차 통계값 (평균, 표준편차, 최대편차 등) 자동 산출

> **분석 단위: 2m × 2m 격자 기준**
> 산출 항목: 구배값(%), 설계기준 대비 편차, 평균편차, 표준편차, 최대편차 자동 계산

#### 9.5.1 본 용역의 해석: "구간" = 2m 격자 셀

세 가지가 이 해석을 가리킨다.

1. **문서가 스스로 분석 단위를 2m x 2m 격자로 명시한다.** 같은 절에서 단위를 정해 놓고 다른
   크기의 "구간"을 따로 요구했다고 읽는 것은 부자연스럽다
2. **산출 항목 줄이 세 통계를 나열형으로 적는다.** 구역별 분해를 요구했다면 "구역별로" 같은
   한정이 붙었을 것이다
3. **"구간별 구배 편차"를 하나의 명사구로 읽는 것이 자연스럽다** - 각 구간(= 셀)의 구배 편차,
   그것의 통계값(평균·표준편차·최대편차)

이 해석에 따르면 요구는 충족돼 있다. `slope_summary`가 2m 셀별 편차에서 `mean_dev_pct`·
`std_dev_pct`·`max_dev_pct`를 내고 판정 불가 셀은 통계에서 제외한다`[구현: engine/flatness/
core/slope.py slope_summary]`. 산출물은 `slope_stats.json`이고, 결과 화면이 "평균 편차 / 편차
표준편차 / 최대 편차"로 표시한다`[구현: dashboard/components/analysis/slope-result.tsx,
slope-verdict-panel.tsx]`.

#### 9.5.2 구역별 분해를 검토했으나 하지 않았다 (실측 근거)

설계 정본`[스펙(구배·정합) §5.4]`은 "구간"을 세부과업 1의 구역화(`core/zones.py`) 결과로
특정했으나, **그것은
스펙 저자의 해석이지 과업지시서의 문구가 아니었다.** 그리고 그 해석대로 붙였다면 **경사 바닥에서
작동하지 않는 알고리즘에 묶일 뻔했다.**

16m x 16m **단차가 하나도 없는 단일 평면**에 `detect_levels` + `build_zones`를 그대로 돌린
결과다`[실측]`.

| 바닥 경사 | z 범위 | 검출 레벨 | 생성 구역 | 구역 면적(m²) |
|---|---|---|---|---|
| 0.5% | 0.083m | 1 | 1 | [256.0] |
| 1.0% | 0.162m | 2 | **2** | [150.0, 106.0] |
| 1.5% | 0.242m | 3 | **3** | [127.1, 106.6, 22.3] |
| 2.0% | 0.322m | 2 | **2** | [186.4, 69.6] |
| **3.0%** | 0.481m | **0** | **0** | **[]** |

원인은 `detect_levels`가 **높이 히스토그램의 봉우리**를 찾는데 경사면은 높이가 균일 분포라
봉우리가 없다는 것이다`[구현: engine/flatness/core/levels.py]`. 노이즈로 생긴 우연한 봉우리를
레벨로 잡고, **3%에서는 어떤 빈도도 `min_frac`(3%)을 넘지 못해 레벨이 0개가 된다.**

**구배 분석의 대상이 바로 설계상 기울어진 배수 바닥이므로 이 실패는 예외가 아니라 정상
케이스다.** 그대로 붙였다면 화면이 존재하지 않는 "구역 1/2/3"의 통계를 내거나 전 셀
`zone_id=None`이 됐을 것이다.

덧붙여 `grade_slope_cells`는 `design_pct`를 **하나만** 받는다. 구역별 설계 구배를 쓰려면
`criteria.thresholds` 스키마와 마이그레이션 007의 기준 5종 시드를 전부 손대야 한다.

**남겨 둔 것**: `SlopeCell`에 `zone_id: int | None` 필드가 **뚫려 있고 항상 `None`**이며
`slope_cells.json` 스키마에도 들어 있다. 후속 단계가 경사 바닥용 구역화 판별식(예: 평면 계수
`(a, b, c)`의 불연속으로 구역을 가르기)을 만들면 **산출 로직만 채우면 되고 산출물 스키마와
화면은 손대지 않아도 된다.**

#### 9.5.3 발주처 판단을 구한다

**"구간"을 발주처가 다르게 해석할 여지가 있다.** 만약 2m 격자 셀이 아니라 방·구역 같은 더 큰
단위를 의도했다면 **현재 산출물은 그 요구를 충족하지 않는다.** 그 경우 필요한 작업은 두 가지이며,
어느 쪽도 현재 범위에 없다.

1. **경사 바닥에서도 성립하는 구역화 판별식 설계.** 현재 구역화는 위 실측대로 경사면에서 무너진다
2. **구역별 설계 구배를 담을 기준 스키마 확장.** 기준 5종의 `thresholds` 형태와 007 시드를 함께
   바꿔야 한다

**본 용역은 해석을 제시하고 판단을 구한다.** 숨기고 넘어가면 나중에 이견이 생겼을 때 되돌릴 수
없기 때문이다.

#### 9.6.2 구배 산출 정확도 실측

과업지시서가 요구하는 **분석 오차율 ±5% 이내**를 게이트로 걸었다. 2.0% 구배 기준이면 0.1%p다
`[구현: engine/tests/test_slope.py]`.

8m x 8m 합성 경사면(설계 구배 2.0%, 내리막 -x 방향, 점 간격 2cm, 서브셀 5cm, 판정 2m 셀 16개,
난수 시드 고정)에 노이즈만 바꿔 주입해 잰 결과다`[실행 확인, 본 보고서 작성 시 측정]`.

| 주입 노이즈 (표준편차) | 최대 구배 오차 | 평균 구배 오차 | 평균 셀 불확도 `se` | 최대 방향 오차 |
|---|---|---|---|---|
| 0 mm | 0.0027 %p | 0.0019 %p | 0.0004 %p | 0.000도 |
| 0.5 mm | 0.0048 %p | 0.0020 %p | 0.0016 %p | 0.066도 |
| 1.0 mm | 0.0076 %p | 0.0020 %p | 0.0029 %p | 0.130도 |
| 2.0 mm | 0.0110 %p | 0.0024 %p | 0.0058 %p | 0.279도 |
| **5.0 mm** | **0.0194 %p** | 0.0087 %p | 0.0144 %p | 0.890도 |

**노이즈 5mm에서도 최대 오차가 0.0194%p로 게이트(0.1%p)의 20% 수준이다.** 이는 **평활도가
노이즈에 지배되는 것(5.4절: 노이즈 1mm에서 결함 없는 평면 전체가 "경계")과 정반대의 결과**이며,
원인은 집계 방식의 차이다. 평활도는 직선자 포락선 아래 **최대** 틈새를 취하므로 무작위 노이즈가
상쇄되지 않고 그대로 편차로 계상된다. 반면 구배는 2m 셀 안 수천 개 서브셀 중앙값에 **최소제곱
평면을 피팅**하므로 노이즈가 평균으로 상쇄된다. 셀별 불확도 `se`가 노이즈에 비례해 커지는 것도
확인된다.

> **그러나 이것은 합성 데이터에 가우시안 노이즈를 준 결과다.** 실제 LiDAR 노이즈는 가우시안이
> 아니고 공간적으로 상관돼 있을 수 있다. **공간 상관이 있는 오차(예: SLAM 드리프트)는 셀 안의
> 평면 자체를 기울이므로 이 상쇄가 통하지 않는다**`[추정]`. 6.1절이 인용한 문헌 조사값에 따르면
> iPhone LiDAR의 SLAM 드리프트는 이동거리의 1~2%인데, 이는 구배 판정 대상 자체와 같은
> 자릿수다. **구배 산출의 현장 실측 대조(레벨 측량)는 수행되지 않았다**(9.6.5절).

#### 9.6.3 설계 정본 §9.3의 복원 게이트를 교체했다

설계 정본이 정한 **원 복원 게이트**는 다음이었다`[스펙(구배·정합) §9.3]`.

> **복원 게이트**(노이즈 1mm, 중첩 50%): 회전 오차 `<= 0.1도`, 평행이동 오차 `<= 1mm`.
> 대응점에 ±5cm 오차(화면 클릭 정확도 수준)를 준 상태에서 ICP가 위 게이트까지 회복하는지.
> **이것이 반자동 정합의 핵심 가정이므로 반드시 검증한다**

**검증한 결과 이 게이트는 달성 불가능함이 확인되어 교체했다.** 지운 것이 아니라 교체했으며,
원 게이트 3줄은 스펙에 그대로 남겼다.

**정확히 무엇이 불가능한가.** 대응점에 클릭 오차가 없으면 원 게이트는 그대로 성립한다(회전
0.00066도, 평행이동 0.126mm). 불가능해지는 것은 여기에 **±5cm 클릭 오차**가 더해질 때다. 즉
알고리즘의 한계가 아니라 **"화면 클릭으로 대응점을 찍는다"는 입력 조건의 한계**다.

**원인은 버그가 아니라 구조적 퇴화다.** 수평 평면은 면내 평행이동 2자유도와 yaw에 대해 정보를
주지 않는다 - 평면을 자기 위에서 밀어도 점군이 그대로라 ICP가 그 방향의 잔차를 줄일 수 없다.
사전조사 실측`[실측]`:

| 픽스처 | 초기 면내 오차 | ICP 후 면내 | ICP 후 z |
|---|---|---|---|
| 무작위 순수 평면 | 169mm | **160.0mm** | -0.000mm |
| 범프 + 단차 | 170mm | 149.4mm | 0.756mm |
| 바닥 + 벽 2면 | 108mm | 135.5mm | -1.783mm |
| 대조: 지터 0 | 0mm | **0.002mm** | -0.001mm |

지터 0 대조군이 0.002mm를 내는 것이 **ICP 자체는 멀쩡함**을 증명한다.

**교체의 근거는 목적 적합성이다.** 면내 오차 `d`가 병합 서브셀 중앙값 z에 주는 영향은
`국소 경사 x d`뿐이다. 구배 2%에서 `d = 150mm`면 3.00mm로 요구 정밀도 ±5mm 안이다. 그래서
**대리 지표(면내 mm) 대신 진짜 계약(중첩 서브셀 중앙값 z 불일치)**을 게이트로 삼았다.

**교체 게이트와 실측값**`[구현: engine/tests/test_registration.py]`. 전부 **표본 독립 픽스처**
에서 잰 값이다(두 스캔이 같은 바닥을 서로 다른 점으로 표본한다).

| # | 게이트 | 조건 | 기준 | 실측 |
|---|---|---|---|---|
| G0 | **원 게이트 유지** (회전 + 평행이동) | 노이즈 1mm, **클릭 오차 0** | <=0.1도 / <=1mm | **0.00066도 / 0.126mm** |
| G1 | z 평행이동 오차 | 노이즈 1mm + 클릭 ±5cm | <=1mm | **0.0080mm** |
| G2 | 중첩 서브셀 중앙값 z 불일치 | 노이즈 1mm + 클릭 ±5cm | <= 노이즈+1mm = 2mm | **0.6629mm** |
| G3 | 최종 RMSE (point-to-plane) | 노이즈 1mm + 클릭 ±5cm | <=2mm | **1.047mm** |
| G4 | 저중첩은 실패로 끝난다 | 실제 중첩 2.57% | `converged=False` + 사유에 "중첩" | **불성립 보고 확인** |

부가 실측: 중첩 50%(원 스펙 명시 조건) z 0.0079mm · RMSE 0.998mm · 수렴. 바닥+벽 장면
RMSE 1.558mm · 수렴. 유령층 15% z 0.0282mm · 수렴.

**회전 오차는 교체 게이트에서 아예 빠졌다.** 클릭 오차 ±5cm에서 실측 yaw 오차가 **0.41283도**로
원 게이트 `<=0.1도`의 **4.1배**이기 때문이다. 회전도 평행이동과 같은 면내 퇴화의 일부이며,
z만 살아남는다. **이 사실을 감추지 않는다** - 9.7절 한계 1이다.

부수 발견 하나를 덧붙인다. **"두 점군의 점이 1:1로 동일한" 픽스처는 정합 테스트를 무력화한다.**
최근접점 탐색이 늘 같은 점을 찾아버려 **바닥을 완전 평면으로 바꿔도 자릿수까지 똑같이 통과한다**
(완전 평면 면내 오차: 1:1 동일점이면 0.026mm, 표본 독립이면 47.15mm). 모든 정합 테스트를 표본
독립 픽스처로 바꾸고, 되돌리지 못하도록 회귀 가드 두 개를 두었다(변이 실험으로 실제로 깨지는
것을 확인).

#### 9.6.4 정합 정확도 실측 전부

아래는 단계 E·F에서 측정한 값 전부다. **모두 합성 픽스처에서 잰 값이며 실물 스캔 대조가
아니다**(9.7절 한계 8).

**(a) 복원 정확도**`[실측]`

| 조건 | 회전 | 면내(수평) | z |
|---|---|---|---|
| 클릭 오차 0, 표본 독립 | 0.00066도 | 0.126mm | - |
| **노이즈 1mm + 클릭 ±5cm** | **0.41283도** | **44.656mm** | **0.0080mm** |
| 위와 같은 조건에서 ICP 전(초기 Umeyama) | 0.46214도 | 51.720mm | -0.261mm |

**ICP는 면내를 14%만 줄이고 z만 33배 개선한다.** 원 설계가 기대한 "ICP가 클릭 오차를
회복한다"는 가정은 **z에 대해서만 참이다.**

**(b) RMSE의 사각지대**`[실측]`

| 바닥 | 수평 어긋남 | point-to-plane RMSE | 판정 |
|---|---|---|---|
| 범프 있는 바닥 | 200mm | 2.865mm | 탈락 |
| **완전 평면** | **1000mm** | 1.004mm | **통과** |
| **완전 평면** | **3000mm** | 1.006mm | **통과** |

정식 실사용 경로 재현(완전 평면, 대응점을 통째로 수평 3m 틀리게 찍음)`[실측]`:

```
면내 3.000m | rmse 1.008mm | converged=True | 사유 없음 | 수평 감도 0.994
```

**세 게이트(RMSE·중첩·발산)가 전부 통과한다.**

**(c) 수평 감도(`horizontal_sensitivity`)**`[실측]` - 정합 결과를 수평으로 ±10cm 밀어 보고
잔차가 오르는 비를 ±x·±y 4방향 중 **최솟값**(최악 방향)으로 잰다.

| 바닥 평탄도 | 감도 |
|---|---|
| ±12mm (이 용역 기준으로는 불합격 바닥) | 1.710 |
| ±6mm | 1.218 |
| **±3.5mm** | **1.084** |
| ±2.5mm | 1.038 |

임계 1.1, **교차점 약 ±4.5mm**다. 즉 **이 용역이 목표로 하는 좋은 바닥일수록 "수평 검증 가능성:
낮음"이 나온다.** 이는 이상이 아니라 "이 바닥에서는 데이터만으로 수평 위치를 판별할 정보가
원래 없다"는 고지다. **구배도 구제하지 못한다** - 최악 방향 집계라 0~20% 램프가 전부 1.002다.

**(d) 겹쳐보기 분해능** (겹친 영역 무늬의 피어슨 상관)`[실측]`

| 픽스처 | 정합이 맞은 경우 | 3m 오정합 | 30cm 오정합 |
|---|---|---|---|
| 특징(요철) 있는 바닥 | +0.996 | -0.176 | - |
| **현실적 ±5mm 평탄 바닥** | **+0.896** | +0.129 | **+0.840** |
| 순수 백색잡음 완전 평면 | +0.014 | +0.043 | - |

**미터급은 확실히 보이지만 30cm급은 정합과 구별하기 어렵고**(0.840 대 0.896), **특징이 없는
평면에서는 신호 자체가 없다**(0.014).

**(e) 구배 적용 범위** (클릭 ±5cm)`[실측]`

| 바닥 구배 | 정합 후 z 오차 |
|---|---|
| 0% | 0.008mm |
| 2% | 0.611mm |
| **3%** | **0.883mm** (z 1mm 회귀 시험 기준의 한계) |
| 5% | 1.477mm |
| 15.0% | 4.841mm |
| **15.5%** | **5.056mm** (±5mm 초과) |
| 20% | 7.037mm |

**z 1mm 시험 기준은 구배 3%까지, ±5mm 요구 정밀도는 15%까지 성립한다.** 통상 바닥 배수구배
1~2%는 여유 있게 범위 안이지만 **주차장 램프급(10~20%)은 범위 밖이다. 그리고 위 전 구간에서
`converged=True`가 나오므로 엔진은 이 열화를 스스로 보고하지 못한다.**

**(f) 클릭 정밀도는 현장 크기에 반비례한다**`[구현: engine/flatness/outputs/height_view.py
_TARGET_LONG_SIDE=256, dashboard/lib/domain/height-view.ts pixelToWorld]`

대응점 좌표는 높이 뷰 격자의 셀 중심으로 양자화되고 **셀 = 긴 변 / 256**이다.

| 현장 긴 변 | 셀 크기 (= 클릭 한 칸) |
|---|---|
| 8m | 3.1cm |
| **약 26m** | **약 10cm (±5cm 가정이 깨지는 지점)** |
| 150m | **58.6cm** |

> **26m는 스펙이 정한 값이 아니라 위 표에서 역산한 값이다**`[추정]`. 엔진이 가정하는 클릭
> 정확도는 `CORR_CLICK_SD_M = 0.05`(±5cm)인데, 두 상수가 코드 어디에서도 연결돼 있지 않다
> (백로그 티켓 90). 가이드라인은 이를 근거로 **한 정합의 커버 범위를 긴 변 26m 안쪽으로**
> 권고한다([`scan-guideline.md`](scan-guideline.md) 9.4절).

**(g) 대응점 개수 효과**`[실측]` - 회전 불확도는 `σ_θ = σ_click / sv1`이고
`sv1 = 측방 RMS 편차 x sqrt(N)`이므로 **점을 더 찍는 것과 더 벌려 찍는 것이 둘 다 듣는다.**
같은 지그재그 배치(6m 기저선·10cm)에서 잰 값이다.

| 대응점 수 N | 3 | 6 | 10 | 20 |
|---|---|---|---|---|
| 측방 RMS 편차 | 0.0472 | 0.0478 | 0.0492 | 0.0498 |
| **`sv1`** | **0.0817** | **0.1172** | **0.1557** | **0.2228** |

> **화면 안내와 문서 권고를 구분해 적는다.** 실제 화면 문구는 **"최소 3쌍이 필요하고 4쌍
> 이상을 권장합니다."** 이고`[구현: registration-workbench.tsx]`, 가이드라인이 권하는
> **8쌍 이상은 위 `sqrt(N)` 관계에서 실무적으로 잡은 선**이지 화면 문구도 스펙 값도
> 아니다`[추정]`.

### 9.9 결론 (세부과업 4)

과업지시서 세부과업 4가 요구한 항목을 **완료 11 · 부분 3 · 의도적 이탈 1**로 구현했다(9.2절).
2m 격자 구배 산출은 합성 데이터에서 요구 오차율 ±5%를 큰 여유로 충족하며(노이즈 5mm에서
0.0194%p 대 게이트 0.1%p), 자동화 테스트 930건이 통과한다(9.6.1절).

동시에 다음을 분명히 밝힌다.

1. **정합의 수평 방향 정확도를 시스템이 보증하지 못한다.** RMSE는 수직 방향만 보고, 수평 감도는
   좋은 바닥일수록 낮게 나오며, 겹쳐보기는 30cm급을 구별하지 못한다. **세 수단이 모두 이 용역의
   대상인 ±5mm 평탄 바닥에서 약하다.** 실질적 보장은 대응점을 넓게 분산해 정확히 찍는 것뿐이며,
   이 한계는 해소된 것이 아니라 **문서로 고지된 상태**다
2. **원 스펙의 복원 게이트는 달성 불가능이 확인되어 교체됐고, 회전 오차는 게이트에서 빠졌다.**
   교체 근거(목적 적합성)와 실측표를 9.6.3절에 전부 적었다
3. **정합·구배의 모든 정확도 수치가 합성 데이터에서 나왔다.** 실물 드론·지상 스캔 대조와 현장
   레벨 측량 대조는 수행되지 않았다
4. **판정 기준 5종 중 재시공 임계는 저장소 관례이고 방향 허용각은 근거 없는 설정값이다.**
   설계 구배·적합 폭 4종만 원문 대조를 마쳤다. **주차장은 배수 최소 구배 기준이 아예 존재하지
   않으며 상한만 있다.** 크기 등급을 그대로 "하자"로 옮기면 하자판정기준 고시와 어긋난다
5. **"구간별 통계"의 "구간"을 2m 격자 셀로 해석했다.** 근거 셋을 9.5절에 적었고 구역별 분해를
   검토했으나 하지 않은 실측 근거도 함께 적었다. **발주처가 다르게 해석한다면 현재 산출물은 그
   요구를 충족하지 않으므로, 해석의 확인을 요청드린다**
6. **구배 결과의 PDF 보고서 편입은 단계 H에서 이행됐고, 남은 것은 렌더 환경 검증이다.**
   구배 분석을 보고서 후보로 고를 수 있고(재판정 중은 선택이 막힌다), 과업지시서 산출 항목
   5개·셀별 결과·`slope_map.png`가 PDF 본문에 실리며 발행본 스냅샷·자산으로 박제된다.
   **다만 렌더 확인은 개발 PC(Windows) Chromium까지이고, 리눅스 컨테이너의 한글 렌더와
   `slope_map.png` 안의 한글 라벨은 배포 후 스모크가 최초 검증이다**(9.2절 마지막 단락,
   한계 12)

1~3번은 실물 데이터·현장 접근이라는 외부 조건이 필요한 항목이고, 4·5번은 발주처·감리의 판단이
필요한 항목이며, 6번은 배포 시 확인으로 닫히는 항목이다. **세부과업 1과 마찬가지로, 본
시스템의 구배 판정도 공식 검측을 대체하지 않는 스크리닝 결과로 운용해야 한다.**
